# Cursor Pagination Model for Timeline APIs

## Executive Summary

Adopt a standard cursor-page model for timeline-style `GET` endpoints using:

- query: `cursor` (opaque, optional), `limit` (optional)
- response payload shape: `data.items[]` plus optional `data.nextCursor`
- ordering: deterministic descending timeline sort with explicit tie-breakers

This keeps API envelope/error behavior unchanged while enabling churn-stable pagination under concurrent writes.

## Standard Response Envelope

ProjectAthena success/error envelopes remain unchanged:

- success: `{ "ok": true, "data": ... }`
- error: `{ "ok": false, "error": { ... } }`

For cursor-paged list responses, standardize success `data` to:

```json
{
  "items": [],
  "nextCursor": "opaque-cursor"
}
```

Contract rules:

1. `items` is always present (empty array when no results).
2. `nextCursor` is optional and omitted when there is no subsequent page.
3. `nextCursor` is opaque to clients (no client parsing contract).

## Standard Query Parameters

For `cursor-page` endpoints:

1. `cursor`
- type: `string`
- optional
- semantics: resume strictly after the referenced row in endpoint ordering

2. `limit`
- type: `integer`
- optional
- default: `50`
- bounds: `1..500` (clamped)

These values align with current control-plane query normalization in `src/control-plane/api-contracts.ts` (`DEFAULT_PAGE_LIMIT=50`, `MAX_PAGE_LIMIT=500`).

## Cursor Key Model (Churn-Stable Recommendation)

### Ordering Contract

Use deterministic descending order (newest first) with immutable tie-breakers:

1. primary timeline field (for example `startedAt`, `requestedAt`, or `createdAt`)
2. `sessionId`
3. `runId` (or stable synthetic legacy id where required for compatibility)
4. endpoint-specific final tiebreaker if needed (for example `pid`)

Rows are returned where `(row sort key) < (cursor sort key)` under this ordering, not by offset.

### Cursor Payload Shape

Cursor should be serialized as base64url(JSON) with:

1. `kind`: endpoint discriminator (for safe decoding/mismatch detection)
2. every field in the ordering tuple

Example (illustrative):

```json
{
  "kind": "active",
  "startedAt": "2026-02-18T10:00:00.000Z",
  "sessionId": "s1",
  "runId": "run_123",
  "pid": 12345
}
```

### Why This Is Stable Under Churn

1. Inserts/deletes before the current page do not shift results like offset pagination.
2. Deterministic tie-breakers prevent duplicates/skips when timestamps collide.
3. Opaque cursor format allows internal cursor evolution while preserving public API shape.

## Backward Compatibility and Deprecation Guidance

1. Continue accepting legacy offset cursors where currently supported.
2. Emit keyset-style `nextCursor` from churn-sensitive timeline endpoints.
3. Deprecate explicit offset query semantics in endpoint docs once keyset is fully adopted.
