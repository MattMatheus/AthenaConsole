# Distributed Locking Backends: Redis vs. Kubernetes Leases

## Executive Summary (Recommendation)

For V1, implement `IDistributedLock` on top of **Kubernetes `Lease` resources** (Coordination API) and ship a **local in-memory lock provider** for local development and tests.

Rationale:
- **Lowest operational overhead** in Kubernetes environments (no new stateful dependency).
- **Adequate latency/performance** for Team Orchestrator’s expected lock frequency (coarse-grained concurrency slots, not high-QPS).
- **Strong client support already in-repo** (`@kubernetes/client-node` is already a dependency).
- Keeps Redis as an optional future backend for non-Kubernetes deployments without blocking V1.

## What We’re Locking (Problem Shape)

Team Orchestrator needs a backend-agnostic distributed lock to enforce global concurrency policies across multiple control-plane instances (e.g., “max N concurrent runs per persona”, “one drain at a time”, etc.).

Key properties desired:
- **Try-acquire with lease/TTL** (lock self-releases if the holder crashes).
- **Best-effort release** (clean unlock when the holder finishes).
- **Low operational coupling** (avoid new infra for V1).
- **Pluggable backend** (local/dev vs. distributed/prod).

## Option A: Redis-Based Locking

### Operational Overhead
- Requires **operating Redis** (or consuming a managed Redis offering).
- Introduces a **new stateful dependency** and associated concerns (HA, backups, networking, credentials, observability).
- If Redis is already present for other reasons, incremental overhead is low; if not, it’s a meaningful addition.

### Latency & Performance
- Very low per-operation latency (typically sub-millisecond in-cluster; single-digit ms cross-zone).
- Suitable for higher-frequency locking patterns.

### Local Development Experience
- Strong: `docker compose up redis` is straightforward.
- Easy to run multiple Team Orchestrator processes locally to validate behavior.

### Client Library Support (Node.js)
- Strong ecosystem (`ioredis`, `redis`, `redlock`-style helpers).
- Requires adding new dependencies and careful integration patterns (safe unlock via value-compare-and-del Lua, clock/TTL choices, etc.).

### Correctness / Risk Notes
- A safe single-instance approach is typically: `SET key value NX PX <ttl>` and release via a compare-and-del script.
- Multi-node algorithms like “Redlock” are debated in the community; adopting them increases complexity and risk.
- Redis failovers/replication modes can produce edge cases depending on topology and consistency guarantees.

## Option B: Kubernetes `Lease` Objects (Coordination API)

### Operational Overhead
- **No additional infrastructure** if Team Orchestrator already runs in Kubernetes.
- Uses the Kubernetes API server + etcd that already exist for cluster operation.
- Requires **RBAC** for the lock manager identity:
  - `get`, `create`, `update`, `patch` on `leases.coordination.k8s.io` (namespaced)

### Latency & Performance
- Lock operations are Kubernetes API calls (often ~10–100ms depending on cluster, auth, and API server load).
- Usually sufficient for coarse-grained control-plane locks (acquire at run start, release at run end, optional periodic renew).
- Not a great fit for very high-frequency locks (tight loops), due to API server QPS/burst limits and latency variance.

### Local Development Experience
- Heavier if you want true distributed behavior locally (need `kind`/`minikube`/`k3d`).
- Practical approach for Team Orchestrator V1:
  - default local development uses the **local lock provider**
  - Kubernetes Lease lock is enabled only when running in a Kubernetes environment (or when explicitly configured)

### Client Library Support (Node.js)
- `@kubernetes/client-node` supports the Coordination API, and is **already in `package.json`**.
- Common patterns exist (Kubernetes leader election uses Leases; the object schema supports TTL-like semantics via `leaseDurationSeconds` and `renewTime`).

### Correctness / Risk Notes
- Leases are designed for **cooperative, TTL-based ownership** (leader election).
- Strong fit for “single holder at a time” locks, and can be adapted for “slot” style locking via either:
  - one Lease per slot (e.g., `persona-foo-slot-1..N`), or
  - a single Lease whose holder identity encodes a single owner (single-slot), combined with higher-level queueing/backoff for contention
- Requires careful handling of optimistic concurrency (`resourceVersion`) to avoid split-brain updates.

## Comparison Matrix (V1 Priorities)

| Dimension | Redis | Kubernetes Lease |
|---|---:|---:|
| Operational overhead (if running in K8s) | Medium–High | Low |
| Latency (p50) | Low | Medium |
| Local dev ease | High | Medium–Low |
| Node client maturity | High | High (and already present) |
| Fit for coarse-grained concurrency gates | High | High |
| Fit for high-QPS locking | High | Low–Medium |

## V1 Recommendation

Implement `IDistributedLock` with:
1. **`LocalMemoryDistributedLock`** (default for local dev/tests; simplest, fast).
2. **`KubernetesLeaseDistributedLock`** (recommended distributed backend for V1 deployments in Kubernetes).

Defer Redis to a later story unless a non-Kubernetes deployment target becomes a near-term requirement.

## Implementation Notes (to Inform Story 03.01 / 03.03)

These are design notes only; they are not implementation requirements yet.

### Suggested `IDistributedLock` Semantics
- `tryAcquire(lockName, { leaseMs, ownerId }): Promise<AcquireResult>`
  - success returns an opaque `lockToken` (used for release/renew)
- `release(lockName, { lockToken }): Promise<void>`
- (Optional) `renew(lockName, { lockToken, leaseMs }): Promise<boolean>` for long-running operations

### Kubernetes Lease Algorithm Sketch
- Map `lockName` → a Kubernetes `Lease` name (DNS-1123 safe; consider hashing long names).
- `tryAcquire`:
  1. `GET` the Lease; if not found, `CREATE` with `holderIdentity=ownerId`.
  2. If found and “expired” (based on `renewTime` + `leaseDurationSeconds`), attempt to `UPDATE`:
     - set `holderIdentity=ownerId`, update `renewTime`, bump `leaseTransitions` (if applicable)
     - include `metadata.resourceVersion` for optimistic concurrency
  3. If found and not expired and holder != owner, acquisition fails (retry with jitter/backoff at a higher layer).
- `release`:
  - best-effort `UPDATE` clearing `holderIdentity` only if current holder matches `ownerId` (CAS via `resourceVersion`).

### Fencing Tokens (Optional but Recommended)
To prevent “stale holder continues after losing lock” hazards, include a fencing token in the acquisition result. Possible sources:
- `spec.leaseTransitions` (monotonic on holder changes) if reliably incremented on each acquire.
- An annotation/counter you increment on acquisition (must be CAS-protected).

The consumer of the lock (e.g., run orchestration) can persist and compare fencing tokens to reject stale actions.

## Follow-Up Triggers (When Redis Becomes Worth It)

Redis becomes a stronger default if:
- Team Orchestrator must run outside Kubernetes but still needs multi-instance coordination.
- Lock operations become frequent enough that Kubernetes API latency/QPS is a bottleneck.
- There is already an organizational standard for Redis and it’s “free” operationally.
