# Runtime Isolation Benchmark (gVisor vs Kata vs Default) - First Pass

## Date

2026-02-18

## Executive Summary

First-pass recommendation:
- Standard workloads default to cluster default runtime (`runc` unless cluster policy overrides).
- High-security workloads should support both `gvisor` and `kata` as selectable profiles behind policy.
- Do not hard-pick one high-security runtime without benchmark data from Athena-like workloads.

Inference from sources:
- gVisor is explicitly designed as a userspace-kernel sandbox for container isolation.
- Agent Sandbox supports runtime class selection and documents both gVisor and Kata pathways.
- Kubernetes `RuntimeClass` is the native abstraction for runtime selection.

## Benchmark Matrix (Initial)

Runtimes:
- `default` (runc)
- `gvisor`
- `kata`

Workload scenarios:
1. short-turn task: single command/tool, <30s expected.
2. medium workflow: multi-step tool chain, 2-5 minutes.
3. cancellation-heavy: repeated cancel at random phases.
4. warm-pool startup: prewarmed claim path where available.
5. cold-start startup: no warm resources available.

Security classes:
- standard
- high-security

## Metrics and Thresholds (Initial Targets)

Primary:
- startup latency p50/p95 (cold, warm)
- end-to-end run latency p50/p95
- cancellation latency p50/p95
- run failure rate (%)
- timeout rate (%)

Resource:
- avg/max CPU
- avg/max memory
- node density impact (runs per node)

Operational:
- debug success rate (how often operator can retrieve useful failure diagnostics in <10 min)
- policy rejection clarity (actionable error context present)

Suggested first-pass pass/fail thresholds:
- failure rate regression vs default runtime <= 2% absolute.
- cancellation p95 <= 5s for all runtimes.
- warm-start p95 must materially improve over cold-start (target >= 30%).
- high-security runtime overhead acceptable if p95 run latency <= 2x default for short-turn tasks.

## Instrumentation Requirements

Team Orchestrator telemetry fields to add:
- `execution.runtimeClass`
- `execution.isolationProfile` (`standard|high-security`)
- `execution.startMode` (`warm|cold`)
- `execution.backend` (`local|sandbox`)
- `execution.latencyMs.startup`
- `execution.latencyMs.runTotal`
- `execution.latencyMs.cancel`
- `execution.outcome` (`ok|failed|timeout|cancelled|rejected`)

## Fixture Summary Artifact Contract (v1)

The runtime isolation smoke fixture now emits a stable machine-readable summary artifact:

- schema version: `athena.runtime-isolation-benchmark.v1`
- fixture version: `1.0.0`
- top-level fields:
  - `generatedAt` (ISO timestamp)
  - `records[]` (sorted by `variantId` then `scenarioId`)
- each record includes:
  - `variantId`, `isolationProfile`, `runtimeClassName`
  - `scenarioId`, `iterations`
  - `startupLatencyMs` (`min|max|p50|p95`)
  - `totalRuntimeMs` (`min|max|p50|p95`)
  - `cancellationLatencyMs` (`min|max|p50|p95|sampleCount`)
  - `outcomeStatusCounts` (`ok|failed|timeout|cancelled|rejected`)

Reference implementation:
- fixture + writer: `tests/helpers/runtime-isolation-benchmark-fixture.ts`
- smoke verification: `tests/runtime-isolation.benchmark-smoke.test.ts`

Execution:

```bash
npm run test:runtime-isolation-benchmark:smoke
```

Interpretation guidance for baseline vs isolated runtime classes:

- compare records with same `scenarioId` across `variantId`s.
- use `startupLatencyMs.p95` for cold/warm startup overhead checks.
- use `totalRuntimeMs.p95` for end-to-end regression checks.
- use `cancellationLatencyMs.p95` and `outcomeStatusCounts.cancelled` for cancellation behavior drift.
- treat increased latency as acceptable only when failure/timeout rates remain within policy.

## Integration Proposal for Team Orchestrator Config (Backward Compatible)

```yaml
execution:
  sandbox:
    enabled: false
    defaultRuntimeClass: ""
    highSecurityRuntimeClass: ""
    fallbackToDefaultRuntimeClass: true
  profiles:
    standard:
      isolationProfile: standard
    high-security:
      isolationProfile: high-security
      requireSandbox: true
```

Behavior notes:
- empty runtime class means cluster default.
- when `requireSandbox=true`, do not silently downgrade to non-sandbox execution.

## Rollout Strategy

1. Canary:
- enable sandbox runtime support for a small subset of non-critical runs.

2. Staged:
- enforce high-security runtime class only for selected personas/roles.

3. Harden:
- promote profile defaults after benchmark + incident review.

## Residual Risks and Unknowns

1. Benchmark portability:
- Results may vary by node type, kernel version, and CNI stack.

2. Tooling compatibility:
- Some tools may behave differently under stronger isolation.

3. Observability gaps:
- Existing Team Orchestrator telemetry may need additional runtime-side details to explain failures.
