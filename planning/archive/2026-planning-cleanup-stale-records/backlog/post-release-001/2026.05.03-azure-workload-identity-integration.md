# M5.03: Transition to Azure Workload Identity

**As a Platform Engineer, I want to use Azure Workload Identity for service-to-service authentication, so that we can eliminate static API keys and follow zero-trust security principles.**

### Problem Statement
We currently rely on static environment variables (like `ATHENA_OPENAI_KEY`) for authentication. This is a security risk and difficult to rotate. Azure Workload Identity allows AKS pods to inherit managed identities for secure access to Azure services.

### User Persona
- **Alex (Platform Engineer):** Wants to minimize the secret surface area and automate identity management.

### Acceptance Criteria
- [ ] AKS cluster is configured to support Workload Identity (OIDC issuer enabled).
- [ ] Managed Identity created and mapped to the AKS Service Account.
- [ ] Application code updated to use `@azure/identity` (specifically `DefaultAzureCredential`) for:
    - Azure OpenAI Service.
    - Azure Key Vault (for any remaining legacy secrets).
- [ ] Local development remains functional via fallback to environment variables or Azure CLI login.

### Risks & Assumptions
- **Assumption:** Azure OpenAI Service supports Azure AD (Entra ID) authentication for the selected region.
- **Risk:** Misconfiguration of the OIDC issuer or Service Account mapping can lead to "Access Denied" errors that are difficult to debug.
