## User Story

As a Team Orchestrator operator, I need the local API service to run due task schedules so configured repeatable work can execute while the app is running.

## Scope

Add the first local due-schedule execution path for task-target schedules stored in SQLite.

## Acceptance Criteria

- Adds a core service/API path that finds due active task schedules at a supplied or current time.
- Runs due task schedules through the existing task workbench execution path.
- Records schedule provenance on created task runs where the current model supports it.
- Updates `lastRunId`, `nextRunAt`, status, and failure policy metadata after schedule attempts.
- Skips missed runs by default rather than catching up multiple occurrences.
- Uses `skip-if-running` as the default overlap policy.
- Emits or records enough missed/skipped/run status detail for later UI/history work.
- Includes focused tests for due execution, skipped non-due schedules, failed task runs, and next-run updates.

## Non-Goals

- No always-on background worker loop.
- No hosted scheduler.
- No schedule UI.
- No mission or workflow-template schedules.
- No catch-up policy beyond skipped missed runs.

## Engineering Handoff

Completed.

Implemented the first local due-schedule execution path for SQLite task-target schedules.

Delivered surfaces:

- `LocalScheduleService.run` now runs SQLite task schedules through `LocalTaskWorkbenchService`.
- `LocalScheduleService.runDue` now combines SQLite due schedules with legacy file-backed schedules.
- Added in-memory `skip-if-running` overlap protection for SQLite schedules.
- Records schedule provenance on created task runs with a `schedule.run.linked` run event.
- Updates schedule `lastRunId`, `nextRunAt`, `status`, and failure-policy attempt metadata after schedule attempts.
- One-shot schedules are disabled after successful execution.
- Failed task runs mark the schedule `error` and preserve the task run id.
- Recurring RRULE schedules advance to the next future occurrence after the tick time, skipping missed occurrences rather than catching up.
- Schedule run API responses can include task target ids, task run ids, next-run timestamps, missed-run timestamps, and skip/failure reasons.

Behavior notes:

- This slice supports `FREQ=MINUTELY`, `FREQ=HOURLY`, `FREQ=DAILY`, and `FREQ=WEEKLY` with optional positive `INTERVAL`.
- Unsupported RRULE shapes fail the schedule attempt and mark the schedule `error`.
- Schedule execution still depends on the target task being runnable by the task workbench. A recurring task schedule can advance to the next occurrence after a successful run, but a later run against the same completed task will fail until the task/workflow-template scheduling model is expanded.
- The always-on background worker loop remains out of scope; `/api/v1/schedules/tick` is the API entry point for due execution.
