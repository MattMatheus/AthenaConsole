# Research: Distributed Locking Backends (Redis vs. Kubernetes)

**As the sole developer, I need to evaluate whether to use Redis or Kubernetes Leases for distributed locking, so that I can choose the backend with the best balance of operational simplicity and reliability for Team Orchestrator.**

## Context
Team Orchestrator is transitioning to a distributed control plane. We need a way to manage global concurrency (e.g., "max 5 concurrent runs per persona") across multiple instances of the management agent.

## Investigation Areas
*   **Operational Overhead:** 
    *   Redis: Requires managing a Redis instance/cluster. 
    *   K8s: Uses native `Lease` resources; no extra infrastructure if already running in K8s.
*   **Latency & Performance:**
    *   Redis: Sub-millisecond locking via RESP.
    *   K8s: Slower (HTTP API calls to Etcd), but potentially sufficient for coarse-grained run concurrency.
*   **Local Development Experience:**
    *   How easily can a developer mock or run these backends locally (e.g., `kind`/`minikube` vs. `docker-compose redis`)?
*   **Client Library Support:**
    *   Evaluate existing Node.js libraries for both backends (e.g., `redlock` vs. K8s client lease management).

## Acceptance Criteria
*   A summary document comparing both backends on the criteria above.
*   A clear recommendation for the V1 implementation.
*   (Optional) A minimal proof-of-concept demonstrating the `IDistributedLock` interface with the recommended backend.
