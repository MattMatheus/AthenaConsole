# Design: RBAC Foundation and Permission Model

**As a developer, I need to define the Role-Based Access Control (RBAC) model early, so that our API resources and endpoints are designed with authorization hooks from the start.**

## Context
While Team Orchestrator is currently a single-user system, it is intended for production environments where multiple operators or service accounts will interact with the API. We need a foundational model that supports "Actions" on "Resources" within "Scopes".

## Scope of Design
*   **Resource Definitions:** Identify the primary resources (e.g., `Runs`, `Workflows`, `Directives`, `Policies`).
*   **Action Mapping:** Define standard actions (e.g., `read`, `create`, `cancel`, `admin`).
*   **Role Definitions:** Propose initial roles (e.g., `Viewer`, `Operator`, `Admin`).
*   **API Integration Strategy:** How will the `control-plane` enforce these checks? (e.g., middleware, decorator-based, or service-layer checks).
*   **Token/Identity Assumption:** Define how identity is passed to the API (e.g., JWT claims, Header-based for local development).

## Non-Goals
*   Implementing a UI for role management.
*   Integrating with OIDC/Auth0 providers (this is a distant goal).

## Acceptance Criteria
*   A design document exists under `planning/architecture/` defining:
    * role model (`Viewer`, `Operator`, `Admin` minimum)
    * resource model and action matrix (`<resource>:<action>` naming convention)
    * scope model (global, persona, run/session where applicable)
*   The design defines request identity shape for v1 (trusted header/local mode assumptions) and a forward-compatible path for token claims.
*   The design provides explicit control-plane integration points (`src/control-plane/services.ts` first, no handler-level authorization business logic).
*   The design includes a backward-compatible migration plan with rollout phases and failure behavior (deny/allow defaults).
*   Follow-on implementation touchpoints are enumerated with proposed test coverage expectations.
