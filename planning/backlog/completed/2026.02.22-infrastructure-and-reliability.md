# M4.02: Implement Infrastructure and Reliability Foundations

**As a Team, we want to implement production-ready infrastructure and reliability patterns, so that we can build, deploy, and operate a stable, observable, and professional-grade service.**

### Problem Statement
Our current application is not production-ready. It lacks a critical health endpoint for monitoring, has no local production-like environment for testing, and suffers from slow, inefficient container builds. These gaps increase deployment risk and slow down developer iteration.

### User Persona
- **Alex (Platform Engineer):** Needs to operate a reliable and stable system.
- **Sam (Developer):** Needs a fast, reliable local environment that mirrors production.

### Acceptance Criteria
- [x] An operational readiness endpoint (`/api/v1/health`) is added to the API service, returning a `200 OK`. An API test is added to verify it.
- [x] A `docker-compose.prod.yml` file is created to run a full production-like build locally, serving static console assets and running the compiled API service.
- [x] Developer documentation is updated with instructions for using the new `podman compose -f docker-compose.prod.yml ...` commands.
- [x] A root `.dockerignore` file is created to exclude common directories (`.git`, `node_modules`, `dist`, `.turbo`, etc.) from container builds, with build time improvements measured and recorded.

### Implementation Notes
- Added `/api/v1/health` route wiring, API contract/schema entries, and API coverage tests.
- Added `docker-compose.prod.yml` with production-like API build + static console via Nginx proxying `/api/*` to the API service.
- Added production Dockerfiles and Nginx config under `packages/core/infrastructure/docker/`.
- Added root `.dockerignore` and recorded measured local context payload reduction from `825,900,457` bytes to `277,442,309` bytes (`66.4%` reduction), documented in `GETTING_STARTED.md`.

### Risks & Assumptions
- **Risk:** The production-like environment drifts from the actual production setup over time.
- **Assumption:** The chosen static web server (e.g., Nginx) is lightweight and sufficient for serving the console assets.
