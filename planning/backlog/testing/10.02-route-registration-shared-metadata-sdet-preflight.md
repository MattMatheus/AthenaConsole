# 10.02 SDET Preflight: Route Registration with Shared Metadata

Phase detection (authoritative): `git status --porcelain` returned empty output on 2026-02-18, so this cycle is in **Preflight**.

## Story Under Test
- Active story: `planning/backlog/active/10.02-refactor-route-registration-with-shared-metadata.md`
- Goal: unify route registration around shared metadata so route families self-describe and server registration becomes deterministic, consistent, and less error-prone.

## Acceptance Criteria (Given/When/Then)

1. Shared metadata contract
- Given route modules define endpoint collections,
- When a module exports routes,
- Then each route entry conforms to one shared route type that includes method, path, handler, and family metadata used by server registration and route-family resolution.

2. Registration source of truth
- Given multiple route modules are present,
- When the API server builds the global route table,
- Then it composes from module exports without duplicating family metadata mapping logic in `src/api/server.ts`.

3. Family resolution determinism
- Given overlapping static and parameterized endpoints across families,
- When `resolveApiRouteFamily(method, path)` is called,
- Then it returns the deterministic family selected by `APIRouter` precedence rules.

4. Backward-compatible API behavior
- Given existing API v1 endpoints,
- When requests are routed through the refactored registration flow,
- Then status codes, envelope shapes, and handler outcomes remain unchanged.

5. Developer documentation
- Given future contributors add or modify route modules,
- When they follow docs,
- Then required route metadata fields and registration pattern are explicit and sufficient to avoid manual server-side mapping edits.

## Requirement Ambiguities and Required Decisions Before Implementation

1. Dynamic collection mechanism
- Ambiguity: "dynamically collects" can mean explicit import aggregation vs runtime filesystem scanning.
- Required decision: keep compile-time explicit import aggregation (deterministic, testable, bundler-safe) unless runtime scanning is explicitly requested.

2. Metadata ownership boundary
- Ambiguity: should core and a2a routes move into modules or stay local in `server.ts`.
- Required decision: either (a) module-ize all families, or (b) document partial scope and enforce one pattern for all extracted route modules.

3. Type boundary for context
- Ambiguity: route modules currently use family-specific context interfaces; story asks for shared route definition.
- Required decision: define whether shared type standardizes only metadata shape or also enforces one common context interface.

4. Duplicate route collision policy
- Ambiguity: expected behavior if two modules export identical method+path.
- Required decision: explicitly accept deterministic precedence or fail fast during registration.

## Missing Failure-Mode Requirements (Must Be Added)

1. Duplicate registration failure path
- Define expected outcome for duplicate method/path across exports.
- Prefer fail-fast with actionable error in startup tests.

2. Invalid metadata path
- Define behavior when module export omits/invalidates family metadata.
- Prefer compile-time type failure and runtime guard in registration builder.

3. Unknown family observability path
- Define how unmatched/undefined family is surfaced in tests and diagnostics.

4. Route precedence regression guard
- Define explicit failure test for family mismatch when static vs parameterized paths overlap.
