# Run Rejection Event Storage Strategy

## Executive Summary (Recommendation)

Adopt a **two-tier strategy**:

1. Keep the current **JSONL append ledger** as the authoritative write path in the near term.
2. Add an optional **derived SQLite read model** for query-heavy or higher-retention deployments.

This aligns with current Stage 8 constraints: no API envelope changes, backward-compatible persistence evolution, and low-risk incremental rollout behind control-plane boundaries.

## Problem Shape

`RunRejectionEvent` history is currently useful for:
- operator troubleshooting (`why was a run rejected?`)
- policy tuning (`which reasons are frequent?`)
- bounded historical APIs (`recent rejection history`)

The storage strategy should optimize:
- queryability (filters, pagination, aggregation)
- scale behavior (write throughput, read amplification, retention)
- operational overhead
- implementation complexity and migration risk
- durability across restarts/crashes

## Option A: JSONL Event Ledger (Current Pattern)

### Queryability
- Good for append + bounded tail reads.
- Weak for multi-dimensional queries and aggregations without full scans.
- Cursor/keyset behavior must be implemented in application code.

### Scale Characteristics
- Writes are fast and simple append operations.
- Read cost grows with file size unless aggressively pruned/segmented.
- Compaction/retention can be deterministic but scan-heavy at larger sizes.

### Operational Overhead
- Very low: no new runtime dependency.
- Works in local/dev and simple single-node deployments.

### Implementation Complexity
- Lowest incremental complexity (already present in Team Orchestrator patterns).
- Easy to preserve existing lock-guarded atomic persistence semantics.

### Retention and Durability
- Durable on disk with existing atomic/lock-safe write patterns.
- Retention requires explicit pruning/rotation policy enforcement.

## Option B: SQLite Table + Indexes

### Queryability
- Strong: indexed filters (`reason`, `sessionId`, timestamps), ordering, windowing, aggregates.
- Simpler to expose stable query surfaces as history grows.

### Scale Characteristics
- Better read scalability than JSONL for filtered queries.
- Write throughput is sufficient for expected rejection event volume.
- Retention can be implemented with bounded `DELETE`/time-window policies.

### Operational Overhead
- Low to moderate: still embedded/local, no external service.
- Requires SQLite availability and schema migration/version management.

### Implementation Complexity
- Moderate: requires schema design, migration path, and backfill/dual-write strategy if introduced.
- Must preserve backward compatibility and fallback behavior when SQLite is unavailable.

### Retention and Durability
- Durable local persistence with transactional semantics.
- Easier integrity guarantees for query state than log scanning.

## Option C: In-Memory Buffer + Periodic Snapshot

### Queryability
- Fast in-process reads for recent data.
- Historical queries depend on snapshot design and reload correctness.

### Scale Characteristics
- Good for small windows; memory pressure grows with retention window.
- Snapshot intervals create durability lag and potential data loss on crash.

### Operational Overhead
- Low external overhead, but higher runtime correctness burden.

### Implementation Complexity
- Moderate/high correctness risk (snapshot timing, crash consistency, replay).
- Harder to keep deterministic semantics under process failures.

### Retention and Durability
- Weakest durability profile unless snapshots are very frequent (increasing write overhead).

## Comparison Matrix

| Dimension | JSONL Ledger | SQLite Table | In-Memory + Snapshot |
|---|---|---|---|
| Query flexibility | Low-Medium | High | Medium (recent window) |
| Read scalability | Low-Medium | High | Medium |
| Write path simplicity | High | Medium | Medium |
| Operational overhead | Low | Low-Medium | Low |
| Migration complexity | Low | Medium | Medium-High |
| Durability | High | High | Low-Medium |
| Fit for current Team Orchestrator baseline | High | Medium-High | Low |

## Recommendation and Rollout

### Recommended Near-Term Decision

- **Primary recommendation:** keep JSONL as authoritative storage for now (lowest risk, preserves current behavior).
- **Planned evolution path:** add an optional SQLite read model once query requirements exceed bounded recent-history scans.

### Why This Fits Current Stage

- Preserves existing API envelope and error semantics.
- Avoids speculative behavior changes in handlers/routes.
- Keeps persistence evolution schema-versioned and backward compatible.
- Maintains lock-guarded/atomic write guarantees for authoritative state.

### Trigger To Adopt SQLite Read Model

Promote SQLite from optional to default when any of these appear:
- frequent filtered queries by reason/session/time across large retention windows
- API latency pressure from JSONL scans
- need for richer aggregation/reporting surfaces

## Non-Goals For This Research Slice

- No schema or runtime implementation changes.
- No API route or envelope behavior changes.
- No migration committed in this story; this document is the decision input for follow-up implementation stories.
