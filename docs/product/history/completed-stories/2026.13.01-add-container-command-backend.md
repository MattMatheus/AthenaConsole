## User Story

As a Team Orchestrator operator, I need assigned task agents to run through a container-command backend so higher-risk local work can execute with clearer workspace and artifact boundaries.

## Scope

Add the first container-command task execution backend while preserving the existing local-process path.

## Acceptance Criteria

- Recognizes manifest-defined container-command agent implementations.
- Starts task run records with backend identity `container-command` or equivalent canonical backend name.
- Enforces workspace and artifact path boundaries before launch.
- Invokes the container command through the runtime backend boundary.
- Records validation, start, log, artifact, completion, failure, and cancellation events consistently with local-process runs.
- Captures final output and artifact metadata when the container command produces them.
- Updates task/run statuses deterministically.
- Supports cancellation for active container task runs where the local container runtime exposes process control.
- Includes focused core tests for manifest validation, boundary enforcement, run/event persistence, output/artifact capture, failure handling, and cancellation behavior.

## Non-Goals

- No hosted remote execution.
- No HTTP/API task backend.
- No plugin registry.
- No global multi-tenant policy system.
- No console backend configuration UI.

## Engineering Handoff

Completed.

Implemented the first container-command task execution path while preserving local-process task execution.

Delivered surfaces:

- Extended `LocalTaskWorkbenchService` with a backend-aware task command resolver for `local-process` and `container-command`.
- Recognizes manifest `implementation.type: container-command`.
- Records container task runs with backend identity `container-command`.
- Requires `implementation.image`, `implementation.command`, and `permissions.containers: allow` for container-command runs.
- Accepts `runtime.preferredBackend: container-command` and keeps compatibility with the earlier `container` backend enum.
- Constrains container working directories to the plugin root before starting a run.
- Starts container commands with scoped environment values from manifest runtime/implementation env fields.
- Emits the same run validation, start, log, artifact, completion, failure, and cancellation events as local-process runs.
- Enforces container artifact metadata storage URIs to stay under `artifacts/`.
- Preserves deterministic task/run status transitions for completion, failure, invalid output/artifacts, and cancellation.
- Updated the v1 agent manifest schema to include `container-command` as a runtime backend option.

Implementation note:

- The first container-command runtime launches the manifest-declared command through the existing local process boundary, with container image metadata recorded on events. This keeps the backend contract and event/status model in place without requiring Docker/Podman availability in unit tests. A later slice can bind `container-command` to a concrete runtime adapter.
