## User Story

As a Team Orchestrator operator, I need a mission to run its ordered tasks sequentially so a repeatable task plan can execute through the existing task-run backends without needing a full DAG scheduler.

## Scope

Add the first mission-run execution path that walks a mission's ordered task list and creates child task runs one at a time.

## Acceptance Criteria

- Adds a mission run API/service entry point that starts a run for an existing mission.
- Creates child task runs through the existing task workbench execution path so backend selection, safety limits, approvals, artifacts, and events remain consistent with manual task runs.
- Executes tasks in mission `taskOrder`, respecting simple `dependsOn` relationships already captured on tasks.
- Stops on the first failed, cancelled, or safety-stopped task by default and records the mission run status accordingly.
- Records mission run lineage so operators can connect the mission run to child task runs.
- Keeps standalone manual task runs first-class and unchanged.
- Includes focused core tests for successful sequential execution, stop-on-failure behavior, and mission/task run lineage.

## Non-Goals

- No full DAG scheduler.
- No parallel mission execution.
- No template-to-mission instantiation.
- No console mission-run UI.
- No natural-language task planning.

## Engineering Handoff

- Added synchronous sequential mission execution through `LocalMissionWorkbenchService.runMission`.
- Mission runs are stored in the existing `runs` table with `targetType: "mission"` and backend `sequential-mission`.
- Mission runs require a ready mission and ordered, attached mission tasks.
- Each child task runs through `LocalTaskWorkbenchService.runTask`, preserving existing backend selection, validation, safety limits, approval events, output, artifact, and task-run behavior.
- Mission execution walks `mission.taskOrder`, checks simple `dependsOn` dependencies against tasks completed earlier in the same mission run, and fails before execution if ordering violates dependencies.
- Mission runs stop on the first child task status other than `completed`; child `failed`, `cancelled`, or `stopped-by-limit` outcomes are reflected on the mission run and mission status.
- Mission run lineage is recorded in the mission run output, returned through service/API detail responses, and captured in mission run events.
- Added `POST /api/v1/missions/:id/run` and `GET /api/v1/mission-runs/:runId`.
- Updated shared contracts, API schemas, route contracts, request parsing, and route registration tests.
- Added focused service/API tests for successful sequential execution, stop-on-failure behavior, dependency ordering, and mission-to-child-run lineage.
