# 2026.1 Release Readiness

## Release Identity

- `release_label`: 2026.1
- `release_type`: local-first release candidate
- `recommended_git_tag`: release-2026.1
- `status`: release validation passed; local release tag ready
- `release_date`: 2026-06-02

`2026.1` is the first date-based Team Orchestrator release train for the current local-first product baseline. Use the human-facing label `2026.1` in docs and release notes. Use `release-2026.1` for a Git tag unless tooling later requires a semver-shaped tag such as `v2026.1.0`.

Internal workspace packages and sample plugins currently remain on `0.1.0`-style semver. That is intentional: product release labels describe the assembled Team Orchestrator app, while package versions describe individually publishable artifacts.

## Release Goal

Ship a coherent local-first Team Orchestrator baseline that a motivated operator can install, run, understand, validate, and extend with plugin-backed agents.

The release is not a hosted multi-tenant cloud product. The supported path is local development or trusted local-server operation.

## Included Capability Baseline

- Web console and local API for agent catalog, tasks, missions, workflow templates, runs, schedules, readiness, events, artifacts, diagnostics, and safety controls.
- Manifest-backed plugins and agents loaded from local plugin paths.
- Durable SQLite app-state for operator-facing control-plane records.
- Workflow-template DAG execution with restart-safe state, recovery, schedule execution, and console graph/status inspection.
- Repository connection and repo-context task creation flows for local work.
- Model provider configuration with readiness checks and provider-backed sample agents.
- Agent Developer Kit package, scaffold command, sample agents, and authoring docs.
- First-run demo workflow that requires no external credentials.
- Product readiness smoke command for a credential-free pass/fail baseline.
- Local-server compose profile, deployment diagnostics, and fresh-server real-work walkthrough.
- Comprehensive user guide and in-product documentation guide.

## Release Validation Gate

Run these checks from the repository root before cutting the release tag:

```bash
npm --workspace @athena/core run typecheck
npm --workspace @athena/core run test:unit
npm --workspace @athena/core run check:schemas
npm --workspace @athena/core run validate:manifests
npm --workspace @athena/console run typecheck
npm --workspace @athena/console run test
npm --workspace @athena/pdk test
docker compose -f docker-compose.local.yml config >/tmp/team-orchestrator-local-compose.yml
docker compose -f docker-compose.server.yml config >/tmp/team-orchestrator-server-compose.yml
./flywheel/tools/validate_workflow_state.sh --format json
git diff --check
```

With the local stack running, also run:

```bash
npm run smoke:product
```

The smoke command must pass against the target release candidate. Provider-backed model execution remains a manual smoke because credentials and model availability are operator-specific.

## Manual Release Smoke

Before tagging, complete one browser pass through the main operator loop:

1. Start the local stack from [Getting Started](../../../GETTING_STARTED.md).
2. Confirm dashboard readiness distinguishes demo readiness from provider or server-hardening warnings.
3. Run the first-run demo workflow from the console.
4. Open the workflow run detail and confirm task-run evidence is visible in workflow context.
5. Open a linked task run and confirm artifact preview state is clear.
6. Connect or select a local repository.
7. Create and run a repo-summary task against that repository.
8. Confirm run output and artifact metadata are inspectable.
9. Open docs from the console and confirm the user guide is reachable.

## Known Non-Blockers

- Hosted multi-tenant deployment is outside the current release scope.
- Package publishing is outside the current release scope; npm package versions remain separate from the product release label.
- Provider-backed smoke depends on external credentials and model availability, so it is documented as manual.
- Advanced admin surfaces may show local-profile or privilege notices when optional APIs are not configured.
- Existing `ATHENA_*` package names and environment variables remain for compatibility even though the product name is Team Orchestrator.
