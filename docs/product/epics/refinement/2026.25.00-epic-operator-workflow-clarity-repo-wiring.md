# Epic 2026.25: Operator Workflow Clarity And Repo Wiring

## Status

Complete.

## Goal

Make it obvious how a local operator wires Team Orchestrator to a repository, understands where agents come from, and starts useful work without needing to author agents inside the console.

## Problem

The console is more coherent after the product-surface polish, but the operating model is still not obvious enough:

- Agents appear in the catalog, but the console does not clearly explain that agents come from local plugins and manifests.
- Operators do not have a clear "add/connect a repo" path that explains how a workspace repository becomes available to tasks, agents, artifacts, and runtime execution.
- The product has task, mission, workflow, schedule, run-template, and resource-control surfaces, but operators can still wonder which primitive they are supposed to create first.
- Resource Controls and advanced pages are now less noisy, but they still do not teach the operator how the system is wired together.
- The first-run demo proves the stack works, but it does not yet bridge cleanly into "use this on my repo."

## Why Now

The first-run path and console polish are complete enough for review. The next product gap is not console-native agent authoring; it is operational clarity. A useful operator needs to know how to connect their repo, where agents are installed from, which primitive to create, and how to inspect the result.

## Scope

In scope:

- Console and docs explanation of the operating model: repos/workspaces, plugins, agents, tasks, workflows, schedules, resources, runs, artifacts.
- Repo/workspace wiring guidance and, where supported by current runtime configuration, UI affordances for adding or selecting a local repository path.
- Agent catalog guidance that agents are installed via plugins/manifests rather than authored directly in the console.
- First-run-to-real-repo transition guidance.
- Dashboard, empty-state, and route-level affordances that direct operators toward the right next action.
- Validation and browser QA for affected console paths.

Out of scope:

- Console-native agent authoring.
- Remote repository cloning, GitHub OAuth, hosted workspace sync, or marketplace installation.
- Remote plugin registry.
- New runtime backend types.
- Compatibility shims for legacy persona or `.athena` authoring paths.

## Constraints

- Preserve the manifest-backed agent and plugin model from ADR-0007 and ADR-0008.
- Keep local repository paths explicit and reviewable; do not hide filesystem ownership.
- Prefer guidance and affordances that match current runtime capability before adding new backend surfaces.
- Do not present agent creation as the normal operator path.
- Keep the first-run path honest: only expose flows that work locally today.

## Recommended Sequence

1. Repo wiring operating model.
2. Agent catalog operating guidance.
3. Repo wiring guidance surface.
4. Create work entry points.
5. First-run to real-repo bridge.

## Risks

- Repo wiring can become confusing if configuration, plugin paths, and runtime workspace roots are described as separate concepts without a simple operator story.
- A console UI that suggests repo connection without actual runtime support would overpromise.
- Over-indexing on docs alone may leave the product feeling like it requires a manual.

## Validation Expectations

- Architecture review before repo-wiring UI implementation if ownership questions remain.
- Console typecheck and lint for UI/copy changes.
- Browser QA for affected routes at desktop and mobile widths.
- Docs link/path smoke checks for README or getting-started updates.
- `./flywheel/tools/validate_workflow_state.sh` after backlog state changes.
