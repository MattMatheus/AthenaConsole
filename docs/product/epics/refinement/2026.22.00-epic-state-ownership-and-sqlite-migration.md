# Epic: State Ownership and SQLite Migration

## Status

Refinement.

## Goal

Make local durable state ownership explicit, reduce split-brain persistence risk, and move operator-facing control-plane resources to SQLite app-state with forward-only migrations.

The target operator and maintainer experience is:

- each state domain has one documented owner,
- startup reports which state stores are active,
- new console/API work knows whether it is reading SQLite app-state or intentional file artifacts,
- migrations happen one domain at a time with focused tests,
- deprecated file-backed control-plane state is removed instead of preserved behind compatibility shims.

## Why Now

The Workflow DAG Engine is complete, and the product now has durable SQLite state for core task, mission, schedule, run, artifact, event, workflow-template, and workflow DAG run surfaces. The remaining maintainability risk from the code-quality audit is that other control-plane resources still live in `FileStateStore` or file-backed managers while product direction says SQLite is the v1 local app-state store.

This epic is not a broad rewrite. It gives the team a map, visible diagnostics, and a safe migration sequence for the domains that should become SQLite-owned.

## Current Baseline

SQLite app-state currently owns:

- plugin and agent indexes,
- workflow-template indexes,
- tasks and missions,
- runs, run events, and artifact metadata,
- schedules and schedule history,
- canonical workflow DAG runs, steps, and events.

File-backed state still participates in:

- sessions and transcripts,
- directives,
- harness profiles,
- run templates,
- deprecated `/api/v1/workflows*` file-backed workflow state,
- work queues,
- run evidence files and specialist artifacts.

Some file-backed state is intentional artifact storage; deprecated file-backed control-plane state should be migrated forward or removed.

## Product Boundary

In:

- state ownership inventory,
- migration sequence and acceptance criteria,
- startup diagnostics for active state stores,
- one-domain-at-a-time migrations for operator-facing control-plane resources,
- removal of deprecated file-backed control-plane ownership where replacement SQLite state exists.

Out:

- all-at-once data migration,
- adding compatibility shims, read bridges, or backward-compatible file-store fallbacks,
- changing run evidence or transcript files that are intentionally artifact-like,
- cloud/remote database support,
- console redesign outside visibility needed for diagnostics.

Acceptance summary:

- Product direction points operators to canonical workflow DAG state only.
- Tests prove canonical workflow DAG routes still cover status and graph inspection needs.

## Validation Expectations

- Architecture story should include docs consistency validation and Flywheel state validation.
- Migration stories should include focused API/service tests for the SQLite-owned path.
- Each migrated domain should prove current product behavior still works without file-store fallbacks unless a story explicitly changes the behavior.
- Full core unit tests should run for each persistence migration.

## Risks

- Migrating multiple domains at once would make regressions hard to isolate.
- Treating artifact files as database rows too early could bloat SQLite and weaken inspectability.
- Removing deprecated file-backed workflow state should wait until canonical workflow DAG coverage is confirmed.

## Non-Goals

- No hosted or multi-tenant database work.
- No broad cloud persistence layer.
- No compatibility shims, read bridges, or long-term support paths for deprecated file-backed control-plane state.
- No large console redesign.
