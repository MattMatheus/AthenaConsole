# Epic 2026.31: Productization, Documentation, And Agent Developer Kit

## Status

Refinement.

## Goal

Move Team Orchestrator from a working local prototype into a product a new operator or agent author can understand, run, extend, and trust without relying on project-history context.

## Problem

The real-work loop now works, but the repository still carries several layers of history:

- legacy Athena-era naming and specialist assets,
- archive and planning records from pre-reset product directions,
- multiple documentation trees with overlapping audiences,
- archived marketing-site history from a previous product direction,
- an existing `@athena/pdk` package that provides useful primitives but is not yet a complete agent developer kit,
- local runtime/build artifacts that appear in working trees and can obscure review.

That clutter makes it harder to know what is canonical, what is historical, what is safe to edit, and how to create useful agents.

## Why Now

The 2026.26-2026.30 arc proved the local real-work path: repo connection, provider setup, model-backed agents, task runs, artifact inspection, and local-server deployment. The next bottleneck is product usability rather than raw capability.

## Scope

In scope:

- Repository cleanup audit with keep/archive/delete recommendations.
- Documentation information architecture for operators, admins, and agent authors.
- Canonical "create your own agent" path that does not depend on tribal knowledge.
- Agent Developer Kit plan and hardening work for package shape, examples, validation, and test harness ergonomics.
- Cleanup of stale public/package metadata that still says ProjectAthena where the current product should say Team Orchestrator.
- Release-readiness smoke checklist that can be run before sharing the project with another user.

Out of scope:

- Public hosted/cloud deployment.
- Marketplace publishing.
- Breaking runtime package renames unless covered by a dedicated migration plan.
- Large feature additions unrelated to making current capabilities usable.

## Cleanup Findings From Initial Scan

- `planning/README.md` remains as a historical pointer while workspace-level onboarding still references old `planning/` handoff paths that no longer exist.
- The stale `apps/marketing/` site was removed from the default product surface after review; archived marketing records remain under `docs/product/archive/`.
- `packages/pdk/` already exists and has valuable agent/persona helpers, but the public path should be framed as an Agent Developer Kit with manifest examples, scaffold guidance, and copy/run tests.
- `specialists/` and `packages/core/src/personas/` are still Athena/persona-centered; some may be valid internal history, but they should be classified before being promoted or removed.
- Product docs are split across `README.md`, `GETTING_STARTED.md`, `docs/developer/`, `packages/core/docs/`, and `docs/product/`.
- Local artifact directories such as `.athena/`, `.turbo/`, `dist/`, `coverage/`, and `.DS_Store` are ignored but present in working trees; cleanup guidance and optional cleanup scripts would reduce review noise.

## Risks

- Cleanup can accidentally remove useful historical context if classification is too aggressive.
- Renaming PDK/package surfaces too early could break examples while the ecosystem is still local.
- Documentation can sprawl again unless each page has a named audience and canonical owner.

## Validation Expectations

- Flywheel workflow validation passes after all queue updates.
- Cleanup audit distinguishes tracked source, ignored generated files, runtime state, and archives.
- Documentation links are checked or manually smoke-tested.
- ADK examples are executable in CI or through a focused local test.
- The first new-user path remains true to the running product.
