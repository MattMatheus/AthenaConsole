# Epic 2026.32: Comprehensive User Documentation

## Status

Intake.

## Goal

Make Team Orchestrator learnable from documentation alone for a motivated user who does not want to read source code to understand the product.

## Problem

The current docs are accurate and organized, but they are still too dense. They mostly tell users where to go and what command to run. They do not yet provide the deeper explanations, examples, mental models, screenshots or API examples, troubleshooting paths, and end-to-end learning sequence that a new operator or agent author needs.

The product has reached a point where the next usability bottleneck is not raw feature capability. It is whether someone can learn the system, trust what it is doing, and recover when setup or runs fail.

## Scope

In scope:

- A comprehensive user guide entry point that explains the product in plain language.
- Concept chapters for agents, plugins, tasks, missions, workflow templates, runs, artifacts, schedules, providers, repositories, safety controls, and local app state.
- Guided workflows with concrete examples:
  - first-run demo,
  - real repository task,
  - provider-backed agent run,
  - agent scaffolding and validation,
  - artifact and event inspection,
  - local-server operation.
- Troubleshooting guidance for common startup, readiness, provider, plugin, repo, and run failures.
- Cross-links from `README.md`, `GETTING_STARTED.md`, and the docs map.
- Validation that examples remain true to current commands and APIs.

Out of scope:

- Rewriting every internal architecture or historical product document.
- Building new product features while writing the guide.
- Hosted/cloud deployment docs beyond existing local-server guidance.
- Marketing-site work.

## First Story

Flywheel item:

- `flywheel/backlog/engineering/intake/STORY-20260530-comprehensive-user-guide.md`

Purpose:

## Risks

- The guide can become another dense index if it only links to existing pages instead of teaching the system.
- Examples can drift unless the guide reuses commands covered by smoke or focused validation.
- The docs must distinguish user-facing concepts from internal Flywheel/product-planning process.

## Validation Expectations

- Docs link/path review over the new guide and entry points.
- Command/API example review against current README, `GETTING_STARTED.md`, package scripts, and smoke command.
- `./flywheel/tools/validate_workflow_state.sh --format json`.
- `git diff --check`.
