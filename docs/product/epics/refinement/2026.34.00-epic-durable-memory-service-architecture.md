# Epic 2026.34: Durable Memory Service Architecture

## Status

Future horizon.

## Goal

Define Team Orchestrator memory as a durable remote-capable service with local-first ergonomics, explicit provenance, and provider-backed storage.

## Problem

The current memory surface is useful as local context search and diagnostics, but it is not sufficient for the product goal. A SQLite file on one machine does not travel cleanly when an operator moves between a laptop, local server, and remote server.

If memory becomes part of the product's value, it must be scoped to an operator, workspace, repository, project, and team rather than to whichever machine happened to run the agent.

## Why Later

This should follow the `2026.1` release candidate. The current release should stay focused on the local-first product baseline. Durable memory is a new platform boundary and should be designed deliberately before implementation.

## Scope

In scope:

- Memory domain model and terminology.
- Provider interface for local, remote HTTP, and future semantic/vector backends.
- Namespace model for account, workspace, project, repository, agent, task, run, and artifact scopes.
- Provenance requirements for every memory write.
- Read/write/delete/archive permissions and approval posture.
- Local cache versus remote source-of-truth boundaries.
- Migration posture for the current local memory search implementation.
- Initial backend recommendation and sequencing.

Out of scope:

- Full remote memory service implementation.
- Semantic/vector retrieval implementation.
- Connector-specific memory ingestion.
- Multi-tenant billing or public hosted deployment.

## Candidate Architecture

Memory should expose a canonical service contract:

- `writeMemory`
- `proposeMemoryWrite`
- `getMemory`
- `searchMemory`
- `listMemory`
- `archiveMemory`
- `deleteMemory`
- `createSnapshot`
- `listSnapshots`
- `restoreSnapshot`

The provider layer should support:

- `local-sqlite`: development, tests, cache, and offline fallback.
- `remote-http`: preferred durable product path.
- `semantic-vector`: optional retrieval backend behind the canonical contract.
- `athena-memory-compatible`: optional adapter if AthenaMemory becomes the backing service.

## Memory Record Shape

Records should include:

- stable id,
- namespace,
- memory type,
- title,
- body or structured payload,
- tags,
- source kind,
- source uri,
- sensitivity,
- retention policy,
- created/updated timestamps,
- provenance linking source agent, task, run, artifact, repository, and operator action,
- optional embedding/index status.

## Story Breakdown

### 2026.34.01 Memory Domain ADR

Purpose:

- Accept the durable memory product contract and remote-source-of-truth stance.

### 2026.34.02 Provider Interface

Purpose:

- Define TypeScript interfaces for memory providers without changing product behavior.

### 2026.34.03 Namespace And Provenance Model

Purpose:

- Specify how memories attach to workspaces, repositories, projects, runs, agents, artifacts, and operator-created notes.

### 2026.34.04 Local Cache Boundary

Purpose:

- Decide which current SQLite/FTS behavior becomes local cache, dev backend, or legacy diagnostic surface.

### 2026.34.05 Remote Backend Recommendation

Purpose:

- Choose the first remote service posture: internal server mode, standalone service, AthenaMemory-compatible service, or hosted database-backed service.

## Success Metrics

- The architecture explicitly rejects copying DB files as the cross-machine memory strategy.
- Future memory work can be implemented against a provider interface without rewriting agent/runtime contracts.
- Agents can declare memory permissions before memory-aware agents are built.
- Local SQLite has a clear role that does not pretend to be durable cross-machine memory.

## Risks

- Designing remote memory too abstractly could delay useful work.
- Choosing a storage backend too early could lock in weak retrieval or sync assumptions.
- Memory scope errors can leak private context between workspaces or repositories.

## Validation Expectations

- ADR accepted.
- Provider interfaces reviewed against current runtime, task, run, artifact, and plugin models.
- Docs identify how current memory commands/API routes map forward.
- Flywheel refinement items are created only after the architecture is accepted.
