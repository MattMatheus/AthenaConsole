# Epic: Operator Readiness And First-Run Experience

## Status

Ready for engineering.

## Goal

Make Team Orchestrator understandable and useful to a new local operator within the first few minutes after clone/startup.

The target operator experience is:

- start the local stack,
- see whether API, console, SQLite app-state, plugin indexes, and runtime dependencies are healthy,
- run a representative sample workflow or task,
- inspect the resulting run, workflow graph, events, and artifacts,
- understand what to try next without reading internal planning history.

## Why Now

The Workflow DAG Engine and State Ownership tracks are complete. The product now has a coherent canonical runtime path and a cleaner persistence model, but the first-run path is still spread across README, Getting Started, console affordances, and implicit sample assets.

The next product step should make the existing foundation easy to understand and verify before adding deeper platform features.

## Product Boundary

In:

- first-run diagnostics and readiness status,
- sample plugin/workflow/demo assets that exercise the current canonical path,
- console empty states and first-action guidance,
- quickstart/docs alignment with actual startup and demo behavior,
- focused tests proving the sample path works.

Out:

- hosted onboarding,
- account provisioning,
- cloud persistence,
- new execution backends,
- broad console redesign,
- marketing site launch work beyond docs alignment.

## Story Breakdown

### 2026.23.01 First-Run Health And Readiness

Flywheel item:

- `flywheel/backlog/engineering/ready/STORY-20260528-first-run-health-readiness.md`

Purpose:

- Give operators a single readiness view/check that explains whether the local system is ready to run useful work.

Acceptance summary:

- Readiness reports API status, SQLite app-state path/migrations, plugin index status, configured runtime/provider posture, and sample/demo availability.
- Console or API exposes readiness without leaking secrets.
- Failures include actionable next steps.

### 2026.23.02 Sample Plugin Workflow Demo

Flywheel item:

- `flywheel/backlog/engineering/ready/STORY-20260528-sample-plugin-workflow-demo.md`

Purpose:

- Provide a durable sample plugin/workflow path that demonstrates the canonical operator loop.

Acceptance summary:

- A sample plugin/agent/workflow template is available in local development.
- The sample can instantiate/run through the canonical workflow DAG path.
- Resulting run status, events, and artifacts are inspectable from current APIs.

### 2026.23.03 Console Empty States And Onboarding

Flywheel item:

- `flywheel/backlog/engineering/ready/STORY-20260528-console-empty-states-onboarding.md`

Purpose:

- Make the console helpful before any user-created data exists.

Acceptance summary:

- Empty states guide the operator to check readiness, inspect agents/plugins, run the sample, or create work.
- The console avoids internal jargon where a first-run operator needs practical next actions.
- Empty states link to real routes and supported workflows only.

### 2026.23.04 Quickstart Demo Docs Alignment

Flywheel item:

- `flywheel/backlog/engineering/ready/STORY-20260528-quickstart-demo-docs-alignment.md`

Purpose:

- Align README, Getting Started, and product roadmap docs with the actual first-run demo path.

Acceptance summary:

- Docs describe one canonical local startup and demo path.
- Commands, URLs, expected health responses, and expected demo outputs match the implemented product.
- Public-facing docs do not depend on internal Flywheel knowledge to explain the product.

## Validation Expectations

- Readiness work should include API/service tests and console tests if UI is changed.
- Sample/demo work should include an integration-style test that exercises the canonical workflow DAG status path.
- Console onboarding work should include focused component or route tests plus browser QA where practical.
- Docs alignment should include link/path checks or focused smoke validation when possible.

## Risks

- Sample assets can drift from real runtime capabilities if they are not tested.
- A readiness screen can become noisy if it reports internal implementation details instead of operator decisions.
- Docs can overpromise if the first-run path depends on local credentials or environment assumptions that are not explicit.

## Non-Goals

- No compatibility shims for removed legacy workflow APIs.
- No hosted onboarding flow.
- No new cloud execution or persistence mode.
- No broad visual redesign beyond empty states and first-run guidance.
