# Epic 2026.33: First Real Work Confidence

## Status

Complete.

## Goal

Make a new single-user or small-team operator confident that Team Orchestrator can move from the built-in demo to useful repository work without hidden source-code knowledge or surprising dead ends.

## Problem

User-level audit found that the console now explains the product reasonably well and the first-run workflow can be executed from the UI. The trust gap appears immediately after the demo, when a user tries to connect repository context, inspect produced artifacts, or understand whether degraded readiness/admin surfaces are blocking real work.

The most important failure is a repo-backed task path that appears valid in the UI and readiness checks, but fails at runtime because the sample repo-summary agent receives `inputs.repo` without the exact `inputs.repo.path` shape it expects. This breaks the first real-work path after onboarding.

## Audit Evidence

- Local stack was running at `http://127.0.0.1:5173` and `http://127.0.0.1:8787`.
- API health was OK; readiness was degraded for local secret-root and unauthenticated external binding warnings.
- The first-run workflow could be instantiated, executed, and opened from the console.
- Opening the demo task artifact produced an "Artifact content not found" message despite the artifact being recorded.
- Workflow run detail showed step status but did not surface the useful task-run output without following separate task-run links.
- Creating a repo-summary task with the ready connected repo "Athena Console QA" saved successfully and reported repo readiness OK, but running it failed with `inputs.repo.path must be a non-empty string.`
- Audit/admin pages resolved to plain "Not found" messages inside otherwise normal console pages.

## Scope

In scope:

- Repairing the connected-repo task input contract so sample repo-backed agents can run successfully from UI-created tasks.
- Making demo and sample artifacts either previewable or explicitly labeled as metadata-only before the user opens them.
- Improving workflow run inspection so operators can see linked task-run outputs/artifacts from the workflow context.
- Separating "demo can run" readiness from server hardening warnings.
- Replacing rough advanced/admin 404 states with clear unavailable or not-configured UI states.

Out of scope:

- Hosted multi-tenant operation.
- Private repository provider authentication.
- General-purpose workflow authoring in the console.
- Broad visual redesign beyond the affected operator paths.

## Success Metrics

- A first-time operator can run the first-run demo, connect/select a ready repository, create a repo-summary task, run it, and inspect the output without using curl or reading source code.
- Readiness warnings clearly distinguish credential-free demo blockers, real-work blockers, and server-hardening warnings.
- Unsupported or metadata-only artifact states are explained before they feel like broken preview actions.
- Advanced/admin pages never render raw "Not found" as the primary user-facing state.

## Risks

- Repo-context compatibility can sprawl if each sample agent expects a different shape. Prefer one documented envelope and compatibility normalization at the boundary.
- Artifact preview fixes should not weaken storage boundaries or allow arbitrary filesystem reads.
- More guidance can become clutter if the console repeats long documentation rather than giving clear next actions.

## Validation Expectations

- Browser QA on the dashboard, workflows, task creation, task run detail, artifact preview, and affected admin pages.
- Product smoke updated or extended to cover a UI-created repo-backed task where practical.
- Focused core and console tests for repo input shaping, readiness classification, artifact preview states, and route/unavailable-state handling.
