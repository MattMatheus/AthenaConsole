# Epic 2026.38: Capability Pack Foundation

## Status

Future horizon.

## Goal

Define and implement the foundation for first-party bundled capability packs made of plugin-backed agents, workflows, docs, fixtures, and tests.

## Problem

Sample plugins prove the manifest model, but new users need built-in capabilities that are useful immediately and that demonstrate what they can build themselves.

First-party packs should use the same plugin system as user-authored packs. Otherwise the product will grow special cases that undermine the agent/plugin model.

## Scope

In scope:

- First-party pack conventions.
- Bundled pack discovery and enablement rules.
- Pack metadata for category, maturity, credential needs, memory needs, and safety posture.
- Workflow-template composition conventions.
- Fixture and test expectations.
- Documentation pattern for pack users and pack authors.
- Console grouping/filtering for bundled packs.

Out of scope:

- Service-specific connector auth.
- Marketplace or remote plugin registry.
- Large new UI for authoring agents in the console.

## Story Breakdown

### 2026.38.01 Pack Manifest Conventions

Purpose:

- Define how first-party packs describe category, maturity, credential requirements, memory usage, safety posture, and example workflows.

### 2026.38.02 Bundled Pack Loader

Purpose:

- Make system/bundled packs discoverable through the same plugin indexing path as local plugins.

### 2026.38.03 Pack Console Grouping

Purpose:

- Group first-party packs in the agent catalog and workflow surfaces without hiding local/user plugins.

### 2026.38.04 Pack Fixtures And Tests

Purpose:

- Require each first-party pack to include fixtures, manifest tests, and at least one smokeable workflow where practical.

### 2026.38.05 Pack Authoring Guide

Purpose:

- Document how users can copy the first-party pattern for their own packs.

## Success Metrics

- First-party packs are normal plugins, not hardcoded product features.
- Users can understand credential and safety needs before enabling a pack.
- Every pack includes runnable or reviewable examples.
- Workflow templates can compose agents from a pack into higher-level work.

## Risks

- Pack metadata can sprawl if it tries to solve marketplace needs too early.
- Bundled packs can crowd the agent catalog if grouping and maturity labels are weak.
- Tests can become brittle if they depend on live third-party services.

## Validation Expectations

- Manifest/schema tests.
- Plugin loader tests for bundled packs.
- Console tests for grouping/filtering.
- Pack fixture validation in CI.
- Documentation link checks or manual docs smoke.
