# Epic: A2A Observability Reframe

## Goal

Prevent pre-reset A2A message-bus observability from steering Team Orchestrator implementation unless it is rewritten against the current run/event/artifact model.

## Product Boundary

A2A is not a near-term internal orchestration primitive for Team Orchestrator. Current orchestration is expressed through:

- agents packaged in plugins,
- tasks and missions,
- workflow template runs,
- run events and artifacts,
- task/run lineage.

Older A2A queue, DLQ, throughput, and stall-alert surfaces are compatibility/legacy observability. They can remain available while old APIs exist, but they should not be presented as a primary product workflow or expanded into new implementation without a new ADR.

## Current Baseline

The codebase still contains pre-reset A2A and work-queue surfaces:

- `/api/v1/a2a/dlq`
- `/api/v1/work/flows/:traceId`
- `/api/v1/work/observability`
- `/api/v1/work/observability/alerts`
- console `DLQ Console`
- A2A observability parsing/query helpers

These surfaces operate over legacy event and queue concepts such as A2A messages, queue throughput, latency heatmaps, and stall alerts. They do not currently model task-run inspection, mission execution, workflow-template DAG state, or agent handoffs as first-class Team Orchestrator concepts.

## Decision

A2A observability is deferred as a standalone product track.

The near-term product should invest in run/event/artifact inspection, workflow DAG status, task/mission lineage, and schedule/run history before adding new A2A message-bus UI.

Existing A2A routes and console surfaces should be treated as legacy compatibility surfaces until one of these happens:

- A new ADR introduces A2A as an external integration boundary.
- A workflow DAG or agent handoff story defines reset-aligned event payloads that need graph visualization.
- The legacy A2A routes are intentionally removed.

## Mapping

| Legacy A2A Concept | Reset-Aligned Mapping |
| --- | --- |
| A2A message | Future external integration event or workflow handoff event, not a core primitive today |
| DLQ item | Legacy queue failure; future equivalent should be run/task failure, schedule history, or integration delivery failure |
| Flow graph | Potential future run lineage/workflow DAG visualization |
| Throughput | Operational telemetry, not a primary operator workflow today |
| Stall alert | Future workflow/schedule/run health signal if backed by current run state |

## First Implementation Slice

`flywheel/backlog/engineering/ready/STORY-20260528-legacy-a2a-surface-labeling.md`

This slice should make the existing visible DLQ/A2A console surface clearly legacy/compatibility-oriented so operators are not led back toward the pre-reset product model.

## Validation Expectations

- Console copy should describe A2A/DLQ as legacy compatibility, not a primary Team Orchestrator workflow.
- Existing A2A API compatibility should remain intact unless a removal story is explicitly approved.
- No new A2A throughput, graph, or DLQ capabilities should be added as part of this reframe.

## Deferred Questions

- Should legacy A2A routes be hidden, deprecated, or removed in a future cleanup?
- Should future external agent-to-agent integrations produce run events, integration events, or both?
- Should workflow DAG lineage reuse any of the old flow graph rendering concepts after reset alignment?
