# Epic: Workflow DAG Engine

## Status

In progress. Foundation complete; executor integration remains.

## Goal

Move workflow templates from sequential mission/task projection toward durable, restart-safe, DAG-capable workflow execution.

The target operator experience is:

- instantiate or schedule a workflow template,
- receive one canonical workflow DAG run id,
- inspect graph status for real task execution progress,
- recover safely after restart,
- and preserve existing mission/task compatibility while the DAG executor matures.

## Why Now

Team Orchestrator can create tasks, group them into missions, instantiate workflow templates, schedule templates, and inspect run history. The durable DAG substrate now exists, but workflow-template execution still mostly follows the mission/task projection path.

The remaining product gap is execution linkage: real task runs need to update workflow DAG steps, schedules need to drive the canonical DAG run, and console surfaces need to inspect actual workflow-template runs rather than seeded DAG state.

Purpose:

- Introduce a service that executes workflow DAG runs by dependency readiness instead of relying only on mission task order.

Acceptance summary:

Delivered:

- Executor selects ready pending DAG steps by run `stepOrder` and runs projected tasks serially through the task workbench.
- Projected task lookup uses existing workflow-template provenance; no schema or API route changes were added.
- Success and failure paths are covered through workflow-template instantiation and workflow status tests.

Status: Completed.

Flywheel item:

- `flywheel/backlog/engineering/done/STORY-20260528-workflow-dag-restart-resume.md`

Purpose:

- Make interrupted workflow DAG runs recoverable and resumable from durable state.

Acceptance summary:

- Startup recovery marks stale running steps resumable with events.
- Resume restarts from failed/stale steps without re-running completed dependencies.
- Status API exposes the resumed state accurately.

Delivered:

- Local control-plane startup now recovers stale running canonical workflow DAG steps.
- Added service-level `resume` on the canonical DAG executor.
- Resume recovers stale steps, prepares failed descendants for retry, resets affected projected tasks to ready, and skips completed dependencies.
- Status API reflects recovered, resumable, resumed, and completed states through existing workflow status responses.

## Tracking Notes

- Stories should stay additive until the DAG executor has proven parity with existing mission/task behavior.
- Prefer compatibility fields and links over response-shape churn.
- Each implementation story should include at least one integration test that starts from a workflow-template instantiation or schedule, not only hand-seeded workflow DAG state.

## Non-Goals

- No hosted scheduler.
- No visual workflow editor yet.
- No automatic planner that invents tasks from natural language.
- No broad replacement of existing mission/task behavior until workflow DAG execution proves out.
- No file-backed state migration outside the workflow execution surfaces named in this epic.
