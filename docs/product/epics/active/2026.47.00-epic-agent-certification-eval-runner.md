# Epic 2026.47: Agent Certification Eval Runner

## Status

Ready.

## Goal

Make first-party agent certification reachable in live product instances by
promoting deterministic golden eval execution from test-only proof into an
operator-triggered product surface that records eval runs and results in
app-state.

## Problem

ADR 0030 is accepted. The certification consumer already exists in
`packages/core/src/control-plane/services/agent-catalog.ts`: certified-maturity
first-party agents require a passing eval run before the agent catalog can report
them as certified. The eval repository and contracts already exist, and
`packages/core/tests/control-plane.software-team-golden-evals.test.ts` proves the
golden fixture loop against a temp SQLite app-state database.

No product code currently calls `appState.evals.createRun` or
`appState.evals.createResult`, so live instances never produce the data that
`evaluateAgentCertification` needs. Certification remains inert until the runner,
API, and console surfaces land.

## Scope

In scope:

- Deterministic, credential-free golden fixture execution for bundled packs.
- A shared eval runner path reused by product code and golden eval tests.
- Eval suite/run/result listing and manual run trigger APIs.
- CLI and admin/operator console trigger entry points.
- Agent-catalog certification details that show latest run status and per-case
  results.
- Safety review of runner shell-out behavior under ADR 0013.

Out of scope:

- Provider-backed, networked, or non-deterministic evals.
- Scheduler-triggered or install-time automatic certification.
- Third-party marketplace certification.
- Declaring bundled packs `maturity: certified` before the runner is shipped and
  passing in product.

## Story Breakdown

### 2026.47.01 Shared Deterministic Eval Harness

Purpose:

- Extract the deterministic golden fixture loop from the software-team eval test
  into reusable core code.
- Define the pack metadata needed to discover fixture roots and deterministic
  runners.
- Keep `control-plane.software-team-golden-evals.test.ts` on the same shared
  implementation path as product code.

Acceptance:

- The software-team golden eval test uses the shared harness.
- The harness rejects provider-backed, networked, or credential-requiring suites
  for v1 certification.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck` and
  `npm --workspace @athena/core run test:unit -- software-team-golden-evals`.

### 2026.47.02 EvalRunnerService

Purpose:

- Add `EvalRunnerService` under `packages/core/src/control-plane/services/`.
- Given a pack id or suite id, load deterministic fixtures, run each case, compare
  expected artifacts, and record `eval_runs` and `eval_results`.
- Reuse the existing eval repository and contracts without adding schema unless
  a small metadata/index change is proven necessary.

Acceptance:

- A manual service call records completed eval runs and pass/fail results for the
  software-team golden suite.
- Failed cases produce failed result rows and a completed or failed run status
  with actionable metadata.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run validate:manifests`.

### 2026.47.03 Eval API And CLI Trigger

Purpose:

- Add the `evals` API route family from ADR 0030.
- Implement `GET /evals/suites`, `POST /evals/runs`, `GET /evals/runs`,
  `GET /evals/runs/:id`, and `GET /evals/runs/:id/results`.
- Add a CLI/admin trigger for manual certification runs.

Acceptance:

- Operators can trigger a deterministic certification run without changing pack
  maturity.
- API responses expose suite, run, result, artifact, and status data needed by
  the console.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run check:schemas`.

### 2026.47.04 Console Certification Surface

Purpose:

- Extend the agent catalog certification block rather than creating a separate
  top-level evals area for v1.
- Show latest run status, per-case pass/fail, suite metadata, and artifact links.
- Add an admin/operator action to run certification manually.

Acceptance:

- An operator can see why an agent is certified, blocked, or not required.
- A running or failed certification has clear status and remediation language.
- Validation commands pass:
  `npm --workspace @athena/console run typecheck`,
  `npm --workspace @athena/console run test`, and
  `npm --workspace @athena/console run build`.

### 2026.47.05 Certification Readiness And Pack Maturity Gate

Purpose:

- Add a readiness check that prevents first-party packs from declaring
  `maturity: certified` unless their deterministic suite passes through the
  product runner.
- Document when bundled packs may move from preview/experimental to certified.
- Capture the ADR 0013 shell-out safety review for deterministic runners.

Acceptance:

- A first-party pack cannot silently claim certified maturity without passing
  product-recorded evals.
- The readiness gate identifies missing fixtures, unsupported runner types, and
  stale passing runs.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`,
  `npm --workspace @athena/core run validate:manifests`, and
  `npm run check:docs`.

## Sequencing And Dependencies

Story 2026.47.01 must happen first so tests and product code share one runner.
Story 2026.47.02 records the data the existing agent-catalog certification
consumer needs. Story 2026.47.03 exposes manual operator triggers. Story
2026.47.04 makes the trust surface visible. Story 2026.47.05 gates certified
maturity after product-recorded passing runs exist.

This epic is independent of workspace/RBAC, but API authorization should use the
current admin/operator controls and align with 2026.44 once server-derived
workspace roles land.

## Acceptance Boundary

This epic is done when deterministic golden certification runs can be triggered
manually, recorded in app-state, queried through API/CLI, displayed in the agent
catalog, and used by the existing certification consumer to report a first-party
agent as certified.
