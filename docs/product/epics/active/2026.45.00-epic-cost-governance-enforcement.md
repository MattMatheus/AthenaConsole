# Epic 2026.45: Cost Governance Enforcement

## Status

Ready.

## Goal

Turn passive cost observability into active governance: budgets, caps, and alerts
that gate runs before spend is incurred, without surprising operators or
breaking the local default path when no budgets are configured.

## Problem

Cost is recorded and reported, but not governed. `task-workbench.ts:2081` writes
usage through `appState.usageLedger.upsert`, and
`operations.ts:253` computes cost summaries from the usage ledger, but there is
no spend cap or pre-run budget enforcement in operations.

There is also an existing orphaned policy field:
`packages/core/src/shared/contracts/policy.ts:70` defines
`costBudgetDailyUsd`, `packages/core/src/api/request-parsers/policy.ts:37`
parses it, `packages/core/src/control-plane/api-schemas.ts:1907` exposes it, and
`packages/core/src/control-plane/services/policy.ts:2042` normalizes it. No
runtime enforcement call site consumes it. ADR 0029 is the source cost-governance
design, but it did not account for this field, so the first implementation story
must reconcile it before adding a new `budgets` table.

This extends ADR 0013's safety family from loop/tool limits and approvals into
spend-facing controls. All spend figures are estimates from
`ProviderTokenPricing`, not provider invoices.

## Scope

In scope:

- Reconcile `costBudgetDailyUsd` into a single budget model or deprecate it.
- Add ADR 0029's budget and budget-alert data model.
- Enforce applicable budgets before model-backed runs start.
- Support `warn`, `require-approval`, and `block` breach actions.
- Surface budget alerts and spend status in the operations console area.
- Add per-workspace budgets and per-user budgets once the workspace membership
  boundary from epic 2026.44 is in place.

Out of scope:

- Redesigning provider pricing.
- Provider billing integration; budgets govern estimated spend only.
- Per-user enforcement across distinct users before 2026.44's server-derived
  membership and scope stories land.
- Interrupting in-flight runs based on mid-run spend.

## Story Breakdown

### 2026.45.01 Reconcile The Existing Budget Field

Purpose:

- Decide whether `costBudgetDailyUsd` becomes the per-policy daily hook into the
  new budget model or is deprecated in favor of the `budgets` table.
- Document the migration and API compatibility behavior.
- Ensure there is a single coherent budget concept after this epic.

Acceptance:

- `costBudgetDailyUsd` is either mapped into the budget model or explicitly
  deprecated with migration guidance.
- No two divergent budget mechanisms remain after the epic.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run check:schemas`.

### 2026.45.02 Budget Data Model

Purpose:

- Implement ADR 0029's `budgets` table with scope type, scope id, provider,
  model, period, limit, thresholds, action, status, and ownership metadata.
- Implement `budget_alerts` and repository methods for budget and alert
  round-trips.
- Map each budget scope to the existing usage-ledger filters.

Acceptance:

- Budgets can be created, listed, updated, and disabled per supported scope.
- Budget alerts are persistent and queryable by budget, period, threshold, and
  status.
- App-state round-trip tests cover budget and alert records.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run check:schemas`.

### 2026.45.03 Enforcement Hook (Pre-Run)

Purpose:

- Evaluate applicable budgets on the run-creation/readiness path before spend is
  incurred.
- Use `ListUsageLedgerOptions` filters for global, agent, provider, model, and
  workspace scopes.
- Implement `warn`, `require-approval`, and `block` actions, reusing the existing
  approval flow for approval-required breaches.
- Record budget-check events with budget ids, scope, estimate basis, current
  estimate, limit, threshold, and decision.

Acceptance:

- A run that would exceed a `block` budget is refused before model-backed work
  starts.
- A `warn` breach records an alert while allowing the run.
- A `require-approval` breach routes through existing approval machinery.
- Readiness output explains that spend is estimated and names the price basis.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck` and
  `npm --workspace @athena/core run test:unit`.

### 2026.45.04 Alerts And Console Surface

Purpose:

- Emit persistent alerts at configured thresholds, including the ADR 0029 default
  80 percent warning and 100 percent breach.
- Extend operations cost surfaces to show budget status, threshold alerts, and
  remediation paths.
- Avoid duplicate alerts for the same budget, period, threshold, and scope.

Acceptance:

- An over-threshold budget creates a visible alert in the operations console
  area.
- Cost summaries show estimate basis and budget/spend status.
- Acknowledging or resolving an alert updates the persisted alert status.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`,
  `npm --workspace @athena/console run test`, and
  `npm --workspace @athena/console run typecheck`.

### 2026.45.05 Per-Workspace And Per-User Scope

Purpose:

- Enforce per-workspace budgets using ledger `workspaceId` filters.
- Add per-user budgets only after epic 2026.44 derives identity and workspace
  membership server-side.
- Ensure budget override/admin capabilities align with workspace role ownership.

Acceptance:

- Per-workspace budgets enforce on the pre-run path.
- Per-user budgets are not enabled until server-derived membership and scope
  from 2026.44.02 and 2026.44.03 are in place.
- Local default operation remains unaffected when no budgets are configured.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`,
  `npm --workspace @athena/core run validate:manifests`, and
  `npm --workspace @athena/console run test`.

## Sequencing And Dependencies

Story 2026.45.01 must happen first so the implementation does not create a new
budget table while leaving `costBudgetDailyUsd` as a second, ignored budget
field. Story 2026.45.02 must precede enforcement because the pre-run hook needs
durable budget definitions. Story 2026.45.05 per-user enforcement soft-depends
on epic 2026.44, specifically 2026.44.02 and 2026.44.03.

All spend is estimated. A wrong price table must not silently block runs without
explaining the estimate basis and remediation path.

## Acceptance Boundary

This epic is done when budgets enforce on the run-creation path with
`warn`, `require-approval`, and `block` actions, threshold alerts surface in the
operations console, `costBudgetDailyUsd` is reconciled rather than orphaned, and
the local default path is unaffected when no budgets are set.
