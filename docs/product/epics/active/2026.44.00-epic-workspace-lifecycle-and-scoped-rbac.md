# Epic 2026.44: Workspace Lifecycle And Scoped RBAC

## Status

Ready.

ADR 0028 is accepted; this epic is the implementation sequence for that
decision.

## Goal

Make workspace a real tenancy boundary with lifecycle management,
server-derived membership, and enforceable per-workspace RBAC, while preserving
the local single-user default path where everything continues to resolve to the
`default` workspace.

## Problem

ADR 0027 accepts the enterprise and multi-user direction, and ADR 0028 defines
the workspace lifecycle and scoped-RBAC design needed to make that direction
safe. The first workspace/RBAC slices are now implemented:

- Workspace lifecycle CRUD exists through app-state repositories, control-plane
  services, API routes, and console surfaces.
- `workspace_members` exists in SQLite app-state and supports per-workspace
  `Viewer`, `Operator`, and `Admin` roles.
- Non-admin workspace scope is derived from server-side membership. The
  `x-athena-scope-workspaces` header is now only an optional narrowing hint, and
  requested workspaces outside membership scope are rejected.
- Admin RBAC exists for workspace and membership management.

The remaining risk is not that workspace membership is absent; it is that every
workspace-owned domain must consistently carry workspace ownership through
storage, query filters, and service authorization. Recent hardening closed
durable-memory namespace authorization and workflow DAG run ownership, but the
enterprise readiness gate still includes continued domain-by-domain
referential-integrity review, cost-governance enforcement, Postgres/server
persistence readiness, and operational deployment hardening.

## Scope

In scope:

- Workspace create, update, list, and delete/block-delete lifecycle.
- A `workspace_members` model with per-workspace roles.
- Server-derived workspace scope and per-workspace RBAC.
- Query-level workspace scoping for user-facing repository reads.
- Referential integrity from workspace-owned rows to `workspaces(id)`.
- Console/admin surfaces required to manage workspaces and memberships.
- A documented multi-user alpha readiness gate.

Out of scope:

- Hosted SaaS operation.
- External IdP integration beyond ADR 0028's server-bound identity model.
- Knowledge-work connector work; that remains gated separately.
- Connector-specific permission redesign.
- Deleting or cascading live run, artifact, memory, usage, or audit evidence.

## Story Breakdown

### 2026.44.01 Workspace Lifecycle CRUD

Purpose:

- Extend `WorkspaceRepository` with create, update, slug lookup, and delete or
  block-delete operations.
- Add admin-only API routes and a workspace-management console surface.
- Protect the seeded `default` workspace from deletion.
- Preserve local/no-auth behavior where existing records continue using
  `default`.

Acceptance:

- Multiple workspaces can be created, listed, renamed, and deleted when empty.
- Attempts to delete `default` fail with an explicit admin-facing error.
- Live workspace-owned records block deletion unless an explicit reassignment
  story has implemented and audited that path.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`,
  `npm --workspace @athena/console run test`, and
  `npm --workspace @athena/console run typecheck`.

### 2026.44.02 Workspace Membership Model

Purpose:

- Add the `workspace_members` table from ADR 0028.
- Add repository methods to assign, update, remove, and list membership.
- Represent per-workspace roles as `Viewer`, `Operator`, or `Admin`.
- Seed or resolve the local default path so auth-disabled installs continue to
  operate in `default` without setup.

Acceptance:

- A subject can be assigned a role on a workspace and that membership round-trips
  through app-state.
- Membership can be queried by workspace and by subject.
- The migration is idempotent for existing local installs.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run check:schemas`.

### 2026.44.03 Server-Derived Scope

Purpose:

- Resolve `scope.workspaces` and per-workspace role from `workspace_members`
  server-side.
- Replace trust in `x-athena-scope-workspaces`; keep the header only as an
  optional narrowing hint after membership lookup.
- Preserve the single-user path: with auth/authz off, requests resolve to
  `default` and current local behavior remains unchanged.
- Apply per-workspace role checks to workspace-scoped operations.

Acceptance:

- A request header can no longer expand workspace confinement beyond
  server-side membership.
- A subject with membership in one workspace cannot access another workspace by
  changing `x-athena-scope-workspaces`.
- Local auth-disabled operation still works without creating membership rows.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run validate:manifests`.

### 2026.44.04 Query-Level Scoping And Referential Integrity

Purpose:

- Move workspace scoping into repository queries for ADR 0028's user-facing
  list/get paths.
- Keep `filterByWorkspaceScope` as defense in depth, not primary isolation.
- Add foreign keys from workspace-owned `workspace_id` columns to
  `workspaces(id)` using ADR 0028's backfill and validation ordering.
- Validate target workspace existence on writes before FK failures are surfaced.

Acceptance:

- Cross-workspace reads are impossible at the query layer for scoped subjects.
- Orphan `workspace_id` rows cannot be written.
- SQLite migrations are split by domain where table rebuilds are required.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`, and
  `npm --workspace @athena/core run check:schemas`.

### 2026.44.05 Multi-User Alpha Readiness Gate

Purpose:

- Add a documented readiness gate before any multi-user exposure.
- Confirm membership-derived scope, per-workspace RBAC, query-level isolation,
  referential integrity, and local default behavior.
- Capture the operator checklist and validation expectations for enabling the
  first multi-user alpha.

Acceptance:

- A readiness document or command clearly reports whether multi-user alpha can
  be enabled.
- The gate fails if workspace scope still trusts
  `x-athena-scope-workspaces` as authority.
- The gate confirms the local single-user path still works unchanged.
- Validation commands pass:
  `npm --workspace @athena/core run typecheck`,
  `npm --workspace @athena/core run test:unit`,
  `npm --workspace @athena/core run validate:manifests`,
  `npm --workspace @athena/console run test`, and
  `npm --workspace @athena/console run typecheck`.

## Sequencing And Dependencies

Story 2026.44.02 must precede 2026.44.03: server-derived scope requires
membership data. Story 2026.44.04 must follow ADR 0028's migration ordering:
backfill and validate before adding workspace foreign keys. Story 2026.44.05 is
the downstream gate for any multi-user exposure.

Plan 026's per-user cost enforcement soft-depends on 2026.44.02 and 2026.44.03.
Knowledge-work connector work remains deferred until these workspace/RBAC
boundaries are clear.

## Acceptance Boundary

This epic is done when workspace scope is server-derived, per-workspace RBAC is
enforced, referential integrity holds for workspace-owned records, query-level
isolation protects user-facing reads, and the single-user local default path
still works unchanged.
