# Epic 2026.43: Knowledge Work Connector Pack

## Status

Deferred until enterprise readiness boundaries are designed.

## Goal

Add first-party connector agents for common knowledge-work systems after the enterprise workspace, RBAC, cost, and persistence boundaries are clear enough to govern external data access.

## Problem

Many operators will want agents to work with planning docs, meeting notes, issue trackers, chat, and personal knowledge systems. These integrations can make Team Orchestrator broadly useful, but they carry higher privacy and auth complexity than local repo workflows.

This epic should choose the first knowledge-work service deliberately rather than trying to support every common SaaS service at once.

This epic is intentionally deferred until the enterprise readiness work has defined workspace membership, server-bound RBAC, cost governance, and durable server-state expectations. Knowledge-work connectors would otherwise add more auth, scope, privacy, memory, approval, and workflow choices before the current platform has the right governance boundaries.

## Scope

In scope:

- Service selection based on user value, auth complexity, API stability, safety, and fixtureability.
- One or two initial knowledge-work connectors.
- Read-first agents for summarization, extraction, planning, and memory ingestion.
- Approved write actions only where the connector platform supports them safely.
- Memory ingestion with provenance and operator review.
- Workflow templates that combine knowledge-work context with software-team or GitHub agents.

Out of scope:

- Broad connector marketplace.
- Background enterprise sync before workspace/RBAC/cost controls are in place.
- Silent ingestion of private workspaces.
- External writes without approvals.

## Candidate Services

Initial candidates:

- Notion.
- Google Drive/Docs.
- Slack.
- Linear or Jira.
- Local document stores.

Selection criteria:

- Clear new-user value.
- Reasonable auth story.
- Stable API and terms.
- Strong fixture and mock testing path.
- Low risk of accidental external writes.
- Useful memory-ingestion story.

## Story Breakdown

### 2026.43.01 Service Selection And Scope

Purpose:

- Pick the first knowledge-work connector service and document why other candidates are deferred.

### 2026.43.02 Read Connector

Purpose:

- Implement read-only access for the selected service through the connector platform.

### 2026.43.03 Knowledge Agents

Purpose:

- Add summarization, decision extraction, action-item extraction, or planning agents depending on the selected service.

### 2026.43.04 Memory Ingestion Review

Purpose:

- Let operators review service-derived facts before promoting them into durable memory.

### 2026.43.05 Knowledge Workflows

Purpose:

- Compose knowledge-work agents with memory and software/GitHub packs.

## Success Metrics

- The first knowledge-work connector is useful without requiring broad workspace permissions.
- Memory ingestion is reviewable and provenance-rich.
- The pack demonstrates how connector agents compose into workflows.
- Deferred services have explicit rationale rather than vague backlog sprawl.

## Risks

- Knowledge-work systems often contain sensitive personal or company data.
- OAuth setup can be too heavy before enterprise admin and workspace controls are defined.
- Service APIs and terms can change, so adapters need clear ownership.

## Validation Expectations

- Service selection record.
- Mock fixture tests.
- Auth/scope readiness tests.
- Memory ingestion review tests.
- Manual smoke with a test workspace or local document fixture.
