# Epic 2026.42: Product Intuition And Start-Work Flow

## Status

Active refinement.

## Goal

Refocus Team Orchestrator around user intent and concrete outcomes before adding more connector surface area.

## Problem

The product vision remains clear: a local, inspectable console where agents do real work safely and operators can understand what happened.

Execution has exposed too many implementation concepts as primary product choices. Operators are asked to choose between agents, tasks, missions, workflows, schedules, run templates, resources, memory, providers, approvals, and diagnostics before they can simply ask for useful work.

Each concept is individually justified, but the cumulative effect makes the product feel like an orchestration framework UI rather than a friendly workbench.

## Scope

In scope:

- Reframe the primary console path around outcomes and capabilities.
- Introduce a start-work flow that lets a user choose what they want done before choosing low-level primitives.
- Rename or regroup operator-facing surfaces so implementation concepts move behind intent-led workflows.
- Reduce first-run and real-work decision count for bundled software-team and GitHub capabilities.
- Keep inspectability, safety, provenance, and plugin-backed extensibility intact.
- Preserve advanced surfaces for authors, administrators, and diagnostics.
- Create explicit UX acceptance criteria for when product nouns are allowed to be first-class navigation.

Out of scope:

- Removing the plugin, agent, task, mission, workflow, run, artifact, approval, memory, or provider domain models.
- Adding new SaaS/knowledge-work connectors.
- Replacing the manifest-backed plugin architecture.
- Natural-language autonomous planning as the default start-work path.
- Hiding safety approvals, proposed changes, or memory write review.

## Product Principle

Primary UX should speak in outcomes:

- "Review this PR."
- "Summarize this repo."
- "Draft release notes."
- "Explain this test failure."
- "Run the demo."

The implementation may still use agents, tasks, workflow templates, missions, DAG runs, artifacts, approvals, and memory records, but the operator should not need to understand those nouns before starting work.

## Target Information Architecture

Primary surfaces:

- Start Work.
- Work History.
- Capabilities.
- Resources.
- Review.

Advanced surfaces:

- Agents.
- Workflows.
- Missions.
- Run templates.
- Policies.
- Audit and diagnostics.

## Success Metrics

- A new operator can start a bundled useful workflow without choosing between task, workflow, mission, or run template first.
- The dashboard gives one obvious next action for first-run and one obvious next action for real repo work.
- Task/workflow implementation details remain inspectable after work starts, but are not required before work starts.
- Existing bundled software-team and GitHub packs are easier to use without adding new capabilities.
- Advanced users can still reach raw agents, workflows, run templates, audit, policy, and diagnostics.

## Risks

- Oversimplification could hide important safety context.
- Renaming surfaces could create temporary documentation churn.
- Start Work could become a vague launcher if capability metadata is not strong enough.
- Moving primitives to advanced navigation could frustrate current power users unless deep links remain stable.

## Validation Expectations

- Product IA decision record.
- Console route/navigation tests where applicable.
- Focused component/model tests for capability selection and preflight behavior.
- Manual browser smoke for first-run demo, bundled software-team work, and GitHub pack work.
- Documentation pass proving the user guide no longer requires the full domain model before the first useful action.
