# Epic 2026.30: Local Server Deployment Readiness

## Status

Complete.

## Goal

Make Team Orchestrator deployable on a local server running containers, with persistent state, connected repos, provider secrets, plugin paths, and readiness diagnostics.

## Problem

The product is local-first today, but a real operator may not want the system tied to a laptop. A local server is the natural next target, especially once agents can run useful repo and research work.

## Why Now

The end of the next roadmap arc should prove that Team Orchestrator can run as a durable local-network service, not just a development stack.

## Scope

In scope:

- Container profile for local-server deployment.
- Persistent volumes for app-state, artifacts, managed repos, plugin packages, and secret material.
- LAN-safe configuration guidance for ports, hostnames, and reverse proxy assumptions.
- Backup/restore notes for app-state and artifacts.
- Startup diagnostics for repo storage, plugin paths, provider configuration, and runtime availability.
- Operator checklist from fresh server to first successful useful run.

Out of scope:

- Internet-facing hosted production.
- Multi-tenant auth.
- Cloud infrastructure provisioning.
- Enterprise observability stack.

## Constraints

- Default to LAN/local-server safety, not public exposure.
- Keep secrets and app-state persistence explicit.
- Avoid requiring platform-specific server tools beyond containers and mounted volumes for the first pass.

## Risks

- Server deployment can expose ports or secrets too broadly if defaults are careless.
- Host/container path translation can confuse repo and plugin setup.
- Deployment work should not distract from proving the real-work loop first.

## Validation Expectations

- Compose config validation.
- Local container smoke with persistent volumes.
- Health/readiness API checks.
- Docs walkthrough smoke from clone to first useful run.
