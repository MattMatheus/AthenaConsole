# Epic: Verification Evidence Model

## Goal

Turn "run completed" into "run completed with inspectable evidence status" without reintroducing a broad pre-reset compliance framework.

## Product Boundary

Evidence is run-scoped proof attached during execution. It can be produced by a runtime backend, an inspectable agent, or a verifier, and it should be inspectable through the same event/artifact surfaces as other run outputs.

Verification is policy evaluation over run evidence. It should produce a clear pass/fail status and actionable failure messages for the operator.

Operator verdicts are human review records. They are not v1 evidence policies, but they can later consume the same run evidence and verification summary.

## Current Baseline

The core package already has a reset-aligned baseline:

- Runtime evidence attachments are persisted as run evidence records.
- Evidence records have a run id, label, type, content, artifact reference, size, and creation timestamp.
- Harness profiles support `require-evidence` verification policies.
- Run results expose `verificationStatus` and `verificationFailures`.
- Session and run inspection APIs already expose run events and artifact metadata.
- ADR 0012 explicitly frames evidence as artifact and output validation.
- ADR 0013 covers stop behavior and preserving inspectable partial evidence.

## Decisions

- No new ADR is required for the first implementation slice; ADR 0012 and ADR 0013 are sufficient.
- Evidence remains run-scoped in v1, not task-level or mission-level policy state.
- `require-evidence` stays the first policy kind.
- Verification failures should be visible in the operator run-inspection workflow before adding broader policy authoring UX.
- Operator-authored verdicts are deferred until verification status is visible and understandable.

## First Implementation Slice

`STORY-20260528-run-verification-inspection`

This slice should make existing verification status and evidence failures visible in the console run inspection page.

## Validation Expectations

- Core contract/type coverage should remain compatible with existing `RunResult` verification fields.
- Console model tests should cover verification status/failure rendering helpers.
- Browser QA should verify runs with passing and failing verification summaries are readable in run inspection.

## Deferred Questions

- Whether operator verdicts should become a distinct resource or event type.
- Whether evidence labels should be registry-backed or remain free-form.
- Whether mission/workflow aggregate verification status should be computed from child runs.
