# Epic 2026.40: Connector Pack Platform

## Status

Complete.

## Goal

Add the platform primitives needed for safe first-party and user-authored connector packs.

## Problem

Connector agents are valuable, but they introduce credentials, scopes, rate limits, external writes, remote data retention questions, and new failure modes. Service-specific connector packs should not be built until the platform has a clear safety and testing model.

## Scope

In scope:

- Connector manifest metadata.
- Credential binding and secret reference model.
- OAuth/API-token posture for first services.
- Declared scopes and permission display.
- Read versus write operation classification.
- Approval requirements for external writes.
- Rate limit and retry conventions.
- Mock fixtures for connector tests.
- Connector diagnostics and readiness.

Out of scope:

- Full marketplace installation.
- Every OAuth provider abstraction.
- Service-specific GitHub/Slack/Notion/Google implementations.
- Background sync at scale.

## Success Metrics

- Connector packs can declare credential and scope requirements before a user runs them.
- External writes are never silent.
- Live-service tests are optional; fixture tests can run in CI.
- Operators can see why a connector is not ready.

## Risks

- Auth abstraction can become too broad too early.
- External write approvals can be bypassed if operation classes are too vague.
- Connector diagnostics can leak sensitive service metadata if not bounded.

## Validation Expectations

- Manifest schema tests.
- Secret binding tests.
- Approval-gate tests for external writes.
- Fixture harness tests.
- Console readiness and scope display tests.
