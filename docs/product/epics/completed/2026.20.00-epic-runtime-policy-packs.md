# Epic: Runtime Policy Packs

## Goal

Make runtime safety choices reusable and inspectable without turning the local-first product into a cluster governance system.

## Product Boundary

A runtime policy pack is a named bundle of execution constraints that can be resolved before a task run starts. It combines:

- allowed backends,
- default and maximum run limits,
- required approval risk classes,
- backend-specific boundary expectations.

Policy packs do not replace agent manifest declarations. They provide product-level presets and guardrails, while agent manifests continue to declare implementation details, supported backends, permissions, and per-agent limit requests.

## Current Baseline

The current task workbench already has reset-aligned safety behavior:

- task runs support `local-process`, `container-command`, and `http-api` backends,
- agent manifests can declare preferred/supported backends,
- local and container task runs are bounded to plugin working directories,
- container artifacts must stay under `artifacts/`,
- runtime duration, output bytes, and artifact limits can stop runs with `stopped-by-limit`,
- approval-required risk classes are emitted as run events,
- ADR 0011 defines backend execution boundaries,
- ADR 0013 defines approval and limit semantics.

## Decisions

- No new ADR is required for the first implementation slice; ADR 0011 and ADR 0013 are sufficient.
- V1 policy packs are local product presets, not remote policy bundles, Kubernetes admission controls, or enterprise compliance packs.
- Policy pack resolution should be deterministic and recorded on the run so operators can inspect why a backend, limit, or approval requirement applied.
- Pack guardrails should compose conservatively with manifest declarations:
  - backend must be allowed by both the pack and the agent implementation,
  - effective limits should use the stricter value when a pack maximum and manifest value both exist,
  - approval requirements should be the union of pack-required and manifest-required risk classes.
- Policy packs should initially be built in code, with persistence/authoring deferred until the operator workflow proves useful.

## First Policy Pack Concepts

### `standard-local`

Default local-first pack. Allows current local task execution defaults and keeps existing behavior compatible.

- allowed backends: `local-process`, `container-command`, `http-api`
- default limits: current task workbench defaults
- required approvals: none beyond manifest declarations

### `cautious-local`

For tasks that should be more tightly bounded on a developer machine.

- allowed backends: `local-process`, `container-command`
- maximum limits: shorter runtime and smaller output/artifact budget than defaults
- required approvals: `shell-command`, `network-write`, `credential-access` when declared by the agent

### `container-isolated`

For tasks where reproducibility or filesystem isolation matters more than convenience.

- allowed backends: `container-command`
- required backend boundary: container implementation with explicit image and artifact path constraints
- required approvals: `container-control` plus any manifest declarations

## First Implementation Slice

`STORY-20260528-runtime-policy-pack-resolver`

This slice should add a core policy pack resolver for task runs and record the resolved pack/effective safety settings in run events. It does not need console authoring or persisted custom packs.

## Validation Expectations

- Core tests should prove backend allowlist, limit composition, and approval union behavior.
- Existing task runs without policy pack declarations should keep current behavior.
- Run inspection should continue to show the existing run events and safety stop details.

## Deferred Questions

- Whether policy packs become persisted operator resources.
- Whether pack selection belongs on agents, tasks, run templates, or all three.
- Whether a console policy-pack management surface is needed before broader runtime isolation work.
- Whether future hosted/cloud backends need a separate organization policy layer.
