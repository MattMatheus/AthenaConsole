# Epic: Run Templates

## Goal

Define run templates as reusable, operator-owned presets for manual single-run execution without duplicating workflow-template or schedule concepts.

## Product Boundary

Run templates are saved run presets. They bind a directive template to a harness profile and default parameter values so an operator can repeatedly trigger the same class of work with small overrides.

Workflow templates are plugin-provided multi-step work definitions. They create tasks, missions, or workflow runs from a reusable template and remain the home for DAG execution, dependency readiness, and restart-safe workflow state.

Schedules are time-based triggers. They do not define work on their own; they point at an existing task, mission, or workflow template and decide when it should run.

## Current Baseline

The core package already has a backend/API/CLI baseline for run templates:

- `GET /api/v1/run-templates`
- `POST /api/v1/run-templates`
- `POST /api/v1/templates/:id/run`
- CLI `run --template <id> --param KEY=VALUE`
- placeholder validation for directive templates and effective run parameters
- run metadata that records template id, harness profile id, and effective parameters

## Decisions

- Run templates remain single-run presets for now, not workflow-template aliases.
- Run templates use existing harness profiles for provider/model/tool policy selection.
- Run templates may be manually triggered immediately. Recurring execution remains schedule-owned.
- The first implementation gap is operator visibility and control in the console, not another backend schema pass.

## First Implementation Slice

`STORY-20260528-run-template-console`

This slice should add a console surface for listing, creating, and triggering run templates against the existing API.

## Validation Expectations

- Core API contracts and server tests continue to cover run-template creation/list/run behavior.
- Console validation should cover API parsing/model helpers for the new surface.
- UI QA should verify an operator can inspect existing templates, create a template, and trigger a run with parameter overrides.

## Deferred Questions

- Whether run templates should later support shared/team-level catalog metadata.
- Whether run templates need import/export through plugin packages.
- Whether schedules should target run templates directly after the console surface exists.
