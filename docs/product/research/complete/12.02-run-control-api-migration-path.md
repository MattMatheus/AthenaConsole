# Run-Control API Migration Path: Session-Scoped to Run-Scoped

## Executive Summary (Recommendation)

Adopt an **additive v1 migration** that introduces explicit run-scoped endpoints under a non-colliding path, while keeping existing session-scoped endpoints unchanged through a deprecation window.

Recommended endpoint shape:
- `POST /api/v1/run-control/by-run/:runId/cancel`

Keep existing endpoint:
- `POST /api/v1/runs/:sessionId/cancel` (legacy-compatible)

This avoids a breaking v1 change, avoids premature full v2 versioning, and provides a clear contract for run-scoped control.

## Current State

- Run creation already produces a unique `runId`.
- Run-control read APIs already expose/filter by `runId`:
  - `GET /api/v1/runs/active`
  - `GET /api/v1/runs/cancel-requests`
- Cancellation write API is still session-scoped:
  - `POST /api/v1/runs/:sessionId/cancel`

## Design Constraint

`/api/v1/runs/:runId/cancel` cannot safely coexist with `/api/v1/runs/:sessionId/cancel` in v1 because both routes have identical path shape and cannot be disambiguated by the router.

## Option Analysis

### Option A: Introduce v2 (`/api/v2/runs/:runId/cancel`)

Pros:
- Clean path design.
- Strong semantic separation by version.

Cons:
- Adds versioning overhead for a narrow surface.
- Requires new v2 route/schema/docs scaffolding before broader v2 scope is justified.

### Option B: Additive v1 non-colliding path (recommended)

Pros:
- Non-breaking for all existing clients.
- Minimal implementation scope.
- Enables immediate run-scoped clients without full version bump.

Cons:
- Introduces a slightly less elegant path (`/run-control/by-run/...`) in v1.

## Recommended API Contract

### New endpoint

- `POST /api/v1/run-control/by-run/:runId/cancel`
- Request body:
  - optional `reason: string`
- Response body:
  - reuse existing `CancelRunResult` envelope semantics (`status: cancelled|not-running`)
  - include `sessionId` for operational continuity with existing clients/logs

### Resolution semantics

- If an active run with `runId` exists, cancel that run.
- If no active run matches `runId`, return success envelope with `status: "not-running"` (parity with existing semantics; no hard error for stale ids).

## Backend/State Implications

- Add control-plane/backend method for run-scoped cancellation lookup (runId -> sessionId active record).
- Keep existing runtime cancellation store as source of truth; add lookup path over active run records.
- Preserve lock-guarded/atomic persistence behavior; no handler-level business logic.

## Migration and Compatibility Plan

1. Add new run-scoped endpoint and contracts.
2. Keep legacy session-scoped endpoint fully supported.
3. Mark legacy endpoint as deprecated in docs/OpenAPI artifact with migration guidance.
4. Collect adoption telemetry (legacy vs run-scoped cancel endpoint usage).
5. Remove or hard-deprecate legacy endpoint only in a future major API version.

## Test and Contract Impact (for follow-on stories)

- Route registration/precedence tests:
  - ensure new path does not collide with existing `/api/v1/runs/*` routes.
- API contract/schema tests:
  - add operation id + response parity for new endpoint.
- API server integration tests:
  - cancel by `runId` success and not-running behavior.
- CLI/API parity tests:
  - preserve existing behavior until CLI migration story explicitly switches write path.

## Non-Goals for This Design Story

- No runtime/control-plane code changes in this story.
- No deprecation enforcement timeline beyond documentation and telemetry recommendation.
